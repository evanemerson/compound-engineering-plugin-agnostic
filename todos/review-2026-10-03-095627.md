# Review — PR #82 (`feat/fenced-block-state-checker`)

Closes residual **2g**. The PR ships a CI-gated checker for "a fenced-block
instruction file must never carry state across a block boundary in a shell
variable", plus its controls suite and four probe fixes.

**Every finding below was reproduced by RUNNING the gate, never by reading the
diff.** That is 2g's own lesson — all six of its shipped instances were found
that way — applied to 2g's gate. Five findings are ways to commit 2g and have
the gate PASS.

All 11 applied in `33976f4` and the follow-up commit; statuses updated in the
same commit per CLAUDE.md.

### 1
status: applied
severity: P1
agent: silent-failure-hunter
category: silent-failure
confidence: 95
action_class: corroborated
file: scripts/check-fenced-block-state.sh
lines: 283-350
title: A drifted extractor output label makes the gate green while parsing nothing

**Problem:** The gate reads the extractor's `--report` by matching literal
labels (`block N:`, `  used-not-assigned:`, `>> 2g DEFECT CANDIDATES:`,
`sources a script`). Nothing pinned that format, and the two files can drift
independently. Measured by renaming one label in a copy of the extractor:
`block N:` → `chunk N:` gave `scope: 0 block(s)`, **0 MISS, rc=0** — a green
gate that parsed nothing, with the `scope:` line printing the evidence of its
own failure while nothing acted on it. (The reviewer's own simulation reported
a silent pass for the `used-not-assigned:` rename too; re-running the real gate
showed leg 3 catches that one at 5 MISS, so only the block-header rename is the
live hole. Corrected here rather than restated.)

**Fix:** New **leg 4** cross-checks the parsed count against two independent
probes — a direct `grep -cE '^block [0-9]+:'` over the same reports, and a
fence count that does not involve the extractor at all. All three must agree,
and a zero parse against a non-zero fence count is its own MISS. Pinned by
`mut_parse_drift`.

### 2
status: applied
severity: P1
agent: adversarial-reviewer
category: correctness
confidence: 96
action_class: corroborated
file: scripts/extract-fenced-blocks.py
lines: 75-80
title: A heredoc body line shaped like an assignment phantom-assigns, suppressing the real candidate

**Problem:** `ASSIGN_RE` scans the raw block body with no heredoc awareness. A
block writing an operator runbook —

```
cat > /tmp/runbook.md <<'EOF'
To reproduce by hand:
P=/tmp/payload.json
EOF
bash client writeback "$P"
```

— reported `assigned: P` from the heredoc **text**, so `$P` stopped being a
candidate, leg 1 saw nothing, and the gate passed a block where `$P` is
genuinely unset. This is the wrong-all-clear direction the file's own comment
argues against for comments. On `compound.md`'s writeback path it is the
v1.26.8 shape: `writeback` falls back to the unscrubbed original, a **PHI
leak**. Not hypothetical — `task.md` block 9 already contains a heredoc.

**Fix:** `mask_heredocs()` blanks heredoc body lines before the assignment
scan. Masking can only make `assigned` SMALLER, the safe direction. The uses
scan is deliberately NOT masked: the shell really does expand `$NAME` in an
unquoted-delimiter heredoc, so masking it would hide a real use. Both
directions pinned (`mut_heredoc_assign`, `mut_heredoc_use`). Corpus-diffed
against `HEAD`: output identical on all 11 command files.

**Problem:** The case's comment claimed "leg 1 is the ONLY leg that can redden
this case." True when written, **false when it shipped**: leg 2s was added
later, block 1 sourced nothing, so leg 2s became a second trigger. Measured —
removing leg 1 killed only `mut_instance3`; `mut_instance5` survived and was a

later leg silently taking over an earlier leg's only headline control.

**Fix:** New `mut_leg1_literal` — a `literal`-class fixture leg 2s
structurally cannot touch, so leg 1 is the single remaining trigger; verified
by mutation, not by argument. Recorded in the shard that the obvious
alternative does NOT work: making block 1 source an unrelated script still
reports 0 MISS, because leg 1 can never fire for a `sourced` name (never
recorded as `assigned` — the reason leg 2s exists). Generalized into a
CLAUDE.md rule: after adding a leg, confirm every leg still kills a case **no
other leg kills**.

because rc alone cannot pin scope: the whole-file mutant stays red by
over-reporting (2 MISSes instead of 1), so the control asserts the exact

title: Leg 4's own probe no-ops when bc is absent, defeating the leg it was added as

**Problem:** Leg 4's extractor-independent probe summed via
`paste -sd+ | bc`. `bc` is a dependency this repo explicitly must not assume —
CLAUDE.md records the identical gap for `jq` ("absent on the primary dev
machine"). Measured with a PATH identical except for `bc`:
`bc: command not found`, then `[: : integer expression expected`, then
**0 MISS, rc=0**, with the `cross-check:` line printing a blank where its count
belongs. The failed substitution leaves the value EMPTY rather than unset so
`set -u` cannot see it, and the `[` error is swallowed because it is an `if`
CONDITION — residual 2i's 2^63 blind spot exactly. An unevaluable leg reading
as a pass, **inside the leg added to stop a probe from silently reading
nothing**.

**Fix:** Pure bash arithmetic, no external calculator, skipping non-numeric
input so a grep failure degrades to 0 — which the `-ne` comparison then
REPORTS as a MISS instead of crashing on. Pinned by `mut_no_bc`, which builds a
PATH missing only `bc` and treats its own inability to do so as a **failure**,
not a pass.

blocks". A real fragment would then be reported as "block sources NOTHING", a
message that never mentions the actual cause. The adjacent `--report` call
already had an explicit arm reading "a tool error is not a finding — this repo
has a recorded incident for reporting one as the other."

**Fix:** Explicit failure arms on both, each a MISS naming it a harness error,
with the `--emit` message warning that subsequent leg-2s findings may be caused
by the failed scan. The leg-0 content scan got the same treatment.
