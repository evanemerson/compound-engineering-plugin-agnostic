- lines: U2 design step 2
- title: The skill-qualifier capture is underspecified in two directions — unbounded token, and no intersection against known skill names
- applied_in: "plan revision, this run (local-only)"

**Problem:** Two personas hit the same underspecified sentence from opposite
sides; anchor promoted 75 → 100 on independent corroboration.

*Feasibility (correctness):* the literal reading of "capturing an optional
same-line skill qualifier preceding the anchor" — take the preceding token,
treat it as a claimed qualifier, validate it against the index — MISSes dozens
of currently-clean citations the moment U2 lands, because ordinary prose sits
directly before the anchor: `review.md:474` "…per §9a", `lfg.md:98` "…the
§2b", `CLAUDE.md:74` "…restated §9a and §9f", `autonomy/SKILL.md:609/648/691/
696/729` "…where §9c", "…outside §9b", "…inside §9b", "…overrides §9b",
"…tier §9c". None of `per`/`the`/`where`/`outside`/`inside`/`overrides`/`tier`
names a skill, so U2's own "0 MISS / 0 WARN" test scenario fails on landing.

*Security-lens (sanitization):* the captured qualifier has no stated charset
or identifier anchor before it resolves to a skill name or path. That is
`argument-sanitization-at-every-shell-out-relay-point.md`'s named gap — "only
a shell-metacharacter charset, no leading-dash ban, no identifier anchor for
single-token slots" — sitting at a relay point U2 deliberately widens to
`.github` and `scripts` content, which on a fork PR is attacker-controlled.

**Fix:** One sentence closes both. A preceding token counts as a qualifier
**only** when, after stripping an optional `<plugin>:` prefix, it matches an
entry in the skill-name set built in design step 1 — and only when it matches
the identifier charset `^[A-Za-z0-9_.:-]+$` with no leading `-`. Any other
preceding word, including ordinary prose, is treated as unqualified and falls
through to the step-4 "any skill defines it" check.
