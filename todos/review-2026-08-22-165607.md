### 1

- status: applied
- severity: P1
- agent: silent-failure-hunter
- category: correctness
- confidence: 100
- action_class: mechanical
- file: plugins/cepa/commands/compound.md
- lines: 183-204
- title: Indented heredoc terminator makes a copied snippet exit 0 having done nothing

**Problem:** The writeback snippet lived inside a numbered list, so every
line — including the `EOF` terminator — carried three spaces of indentation.
An unquoted heredoc requires its terminator at column 0. Reproduced locally:
bash does not recognize the indented `EOF`, consumes the rest of the script
as heredoc body, emits only a **stderr warning**, and **exits 0**. The
`writeback` call and the entire promote loop never execute. An agent copying
the block as rendered — the intended use of a "copyable envelope" — performs
no writeback and reports a clean run. `<<-` does not fix this (it strips
tabs, not spaces), and using it would move the breakage into the Python body
as an `IndentationError` (verified).

**Fix:** Removed heredocs from Step 4.6 entirely. The payload is now built
with the **Write tool** (no shell quoting, no terminator, no indentation
hazard), and the remaining bash is terminator-free. Verified by extracting
both fenced blocks **with indentation preserved** and checking: 0
heredoc-EOF warnings, no `<<` remaining in the step.

### 2

- status: applied
- severity: P1
- agent: silent-failure-hunter
- category: error-handling
- confidence: 100
- action_class: mechanical
- file: plugins/cepa/commands/compound.md
- lines: 216-228
- title: Non-2xx writeback collapses into "0 ids to promote" — the degrade rule can never fire

**Problem:** A rejected writeback (400/422/5xx) writes an error body to
`$P.resp` and exits nonzero, but the snippet had no exit check. Execution
fell through to the python3 parse, which threw `KeyError: 'memories'`
(also unchecked), leaving `$P.ids` empty; the promote loop then iterated
zero times and exited 0. A failed write was bash-indistinguishable from
"wrote 0 rows". This contradicted the step's own text one paragraph earlier
about the mid-run degrade rule — nothing detected the 400, so nothing could
degrade.

**Fix:** Explicit `if ! bash "$CLIENT" writeback ...` branch that echoes the
response body and exits nonzero, plus a matching guard on the parse.
Verified with stubs: a 400 exits 1 printing the error body; a 200 with an
unparseable body exits 1 printing `UNPARSEABLE`.

### 4

- status: applied
- severity: P2
- agent: previous-comments-reviewer
- category: correctness
- confidence: 95
- action_class: corroborated
- file: plugins/cepa/commands/compound.md
- lines: 191
- title: idkey hashed the source doc instead of the payload file

**Problem:** `brain-client.sh idkey` takes the **payload file** as arg 3
(enforced by `[ -f "$3" ]`, documented that way in SKILL.md), so the
idempotency key tracks the strings actually written. The snippet passed the
doc path as both arg 2 and arg 3, and computed it *before* the payload
existed. An edit changing only the extraction would reuse a key and dedup
away; a doc edit not changing the extracted strings would force new rows.

**Fix:** Reordered — payload is written first, then
`idkey "$REPO" "$DOC" "$P"`, then the key is merged in. Verified live: the
key is derived from the payload file's hash.

- title: "Promote the ids the call DID return" is unachievable on a 5xx

**Problem:** The contract told callers to promote returned ids on a partial
5xx. Reading the deployed handler settles it: on a mid-loop error the API
returns only `{error}` and **discards its `created` array**, so ids for rows
already committed never reach the caller. The instruction described an
impossible recovery and implied a safety property that does not exist.

**Fix:** Corrected to state that those rows are stranded and unrecoverable
from the client, that a non-2xx means "this doc needs a re-run", and that the
stable idkey makes the re-run safe because its 200 response re-surfaces the
already-inserted ids — the only route to promoting them.
