Three roster agents (security-sentinel, architecture-reviewer,

### 1

- status: applied
- severity: P1
- agent: architecture-reviewer
- category: correctness
- confidence: 95
- action_class: mechanical
- file: plugins/cepa/commands/setup.md
- lines: 217-220
- title: Step 3 read `$CEPA_ROOT` from a different shell than Step 1 set it in

**Problem:** Step 1 resolved `$CEPA_ROOT` inside its fenced block; Step 3's CI-template
path referenced it as "the root resolved in Step 1". Each fenced block is a separate
Bash invocation and shell state does not persist between them, so Step 3's `cp` would
read from `/templates/ci/`. This is the **same defect class as the bug being fixed** — a
value set in one shell assumed available in another. Verified empirically: a variable
exported in one Bash tool call reads as unset in the next.

**Fix:** Step 3 now re-runs the resolver loop in its own block with its own guard, and
Step 1 carries an explicit note that `$CEPA_ROOT` does not survive to the next step.

### 2

- status: applied
- severity: P1
- agent: architecture-reviewer
- category: correctness
- confidence: 95
- action_class: mechanical
- file: plugins/cepa/commands/setup.md
- lines: 32
- title: Step 1's health-script call was unguarded, reintroducing the 127 it fixes

**Problem:** If the bootstrap loop matched no candidate, `$CEPA_ROOT` stayed unset and
execution fell through to `bash "$CEPA_ROOT/scripts/check-health.sh"` → `bash
"/scripts/check-health.sh"` → exit 127: exactly the failure this PR exists to remove.
`compound.md` had a guard; this site did not.

**Fix:** Added the explicit `[ -n "${CEPA_ROOT:-}" ] || { …; exit 1; }` guard, whose
message states this is path resolution and forbids falling through to the manual checks.

### 3

- status: applied
- severity: P1
- agent: security-sentinel
- category: security
- confidence: 90
- action_class: corroborated
- file: plugins/cepa/scripts/resolve-plugin-root.sh
- lines: 105-133
- title: Repo-local resolution made an untrusted clone a code-execution vector

**Problem:** The `git rev-parse --show-toplevel` leg resolved `plugins/cepa` from
whatever repo the cwd happened to be in. Reproduced concretely: stage any git repo
shipping `plugins/cepa/scripts/{resolve-plugin-root.sh,brain-client.sh}`, run a cepa
command with cwd inside it, and the caller's bootstrap loop sources the hostile
resolver, which self-locates into that repo and returns it as `$CEPA_ROOT`; the command
then executes the attacker's `brain-client.sh` with the payload path as an argument.
Reviewing an untrusted clone is an ordinary activity, so "cwd happens to be here" must
not be sufficient to win.

**Fix:** That leg is now opt-in via `CEPA_DEV=1`, in the resolver and in all five caller
loops. No in-repo marker could gate it instead — a name in `plugin.json`, a
`marketplace.json`, a directory layout are all forgeable by whoever planted the scripts;
only a signal from outside the repo is trustworthy. Verified: attack blocked, and the
legitimate self-development case still resolves with `CEPA_DEV=1`.

**Note on the agent's severity reasoning, corrected by measurement:** the agent claimed
this leg beat the marketplace glob. It does not — the caller loop tries the marketplace
first, so once the resolver ships, a real install already wins. The attack requires no
installed cepa (or a pre-merge one). Still fixed, at the agent's severity, because the
hostile-repo path is real and the leg serves only self-development.

**Problem:** Three of four sites enforced the unresolved-root case in executable code

a `health` pre-check, and states that every later verb call repeats both. Prose-only
enforcement was already shown insufficient by the original bug.
