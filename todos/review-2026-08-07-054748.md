### 1

- title: Stale run selection produces a live false positive today

**Problem:**
Raised by feasibility and independently by adversarial, then re-measured
directly. Step 2 selects each workflow's newest *completed* run on the default
branch with no check that the run is at the branch tip. Measured 2026-08-07:

| workflow | newest run on main | at tip `e6565ca`? |
|---|---|---|
| model-pins | `e6565ca` | yes |
| changelog | `68740cd` (PR #39) | **no** |
| mutation-sweep | `929354f` (08-03) | **no** |

`changelog` runs only on release events and `mutation-sweep` only weekly, so
both still sit at commits *before* PR #40 fixed the pin — and their annotations
still name the old node20 SHA. Shipping as written, the observer's first act
would have been to warn and open an issue about an already-closed finding.

The plan's own "Precise — present exactly when there is a problem" claim was
true only for workflows that re-run on every push.

**Fix:**
Applied. The run's `head_sha` is compared to the default branch tip; a mismatch
routes that workflow to UNVERIFIED with the reason printed, reusing the existing
bucket rather than adding an escalation path. Verified end-to-end against the
live API: `changelog` and `mutation-sweep` are skipped as stale, `model-pins` is
inspected clean.

### 2
- status: applied
- severity: P1
- agent: adversarial
- category: Adversarial
- confidence: 75
- action_class: gated_auto
- file: .github/workflows/model-pins.yml
- title: Escalation never reaches a hard stop

**Problem:**
The predecessor's finding 5 prescribed *two* stages — warn for the lead time,
MISS in a short hard window. This plan quoted finding 5 to justify dropping the
MISS and never re-added the second stage, so nothing ever goes red. "Revisit if
an issue is closed without the pin being bumped" requires someone already
watching the issue tracker, which is what "nothing was watching" already
disproved once here.

**Fix:**
Applied, but **not** as the suggested countdown to a hardcoded removal date —
that would reintroduce the policy table this redesign deleted, and a date list
is precisely what goes stale. The clock is the tracking issue's own
`created_at`: the check MISSes once the issue has been open longer than
`ESCALATE_AFTER_DAYS` (21). No external calendar, self-updating across every
future runtime cycle, and it measures the thing actually worth reddening a PR
over — this has been ignored for three weeks.

### 7
- status: applied
- severity: P1
- agent: verification
- category: Verification
- confidence: 100
- action_class: mechanical
- file: .github/workflows/model-pins.yml
- title: The escape-hatch guard matched its own source

**Problem:**
**Not found by the panel — found by running the code.** The first cut was
`grep -rn 'ACTIONS_ALLOW_USE_UNSECURE_NODE_VERSION' .github/`, whose pattern is
itself a literal inside `.github/workflows/model-pins.yml`. On a clean tree the
grep matched its own line, so the step was **permanently red** from the first
commit. Reproduced: exit 1 with the tree clean.

This is the same class as the live open defect in `check-model-pins.sh` leg 4 —
a scan whose root contains the file declaring it — committed inside the PR that
cites that defect as the thing it avoids by construction. A detector is not
exempt from the class it detects, now for the fourth time on record here.

**Fix:**
The needle is assembled at run time (`"…NODE""_VERSION"`) so the literal never
appears in the file, matching the precedent where sibling scripts construct a
section sign rather than writing one. Proven green → red → green, and the step
prints the assembled needle so a reader can see what was actually searched for.
