**Problem:** `(-[0-9]*[A-Za-z]+)*` does not stop at a word boundary. An anchor
followed by a hyphen and a plain English word parsed as a range whose second
endpoint was that word. Reproduced: one sentence containing two such compounds
appended to `CLAUDE.md` produced two MISSes naming anchors that appear nowhere
in the repo, against prose the author wrote correctly.

The rewrite **widened** this. On identical input the pre-rewrite script
produced one MISS, not two, because the single-letter class truncated the tail
to a *real* anchor and passed silently. So round 1 correctly killed a silent
wrong-resolve and simultaneously converted it into a guaranteed false positive.
Both halves close together.

**Fix:** `(-[0-9]+[A-Za-z]+)*` — endpoints numbered on both sides, matching the
only range form that exists in the repo. The convention this enforces (ranges
are written fully numbered; an unnumbered tail checks only the first anchor) is
now stated at the regex. Verified: repo green at 30 pairs; hyphenated compounds
produce 0 MISS; a range with a bad numbered endpoint still MISSes.

**Problem:** Two findings that are one defect, so merged and treated as

*The hole:* `grep -ahoE` is line-based, and `CITE_RE`'s qualifier group ends in
`[[:space:]]+`, which would match a newline but is never presented with one.
This repo hard-wraps prose at ~76 columns, so ordinary reflow routinely puts the
owner token at the end of one line and the anchor at the start of the next.
When it does, the match is the bare anchor, the qualifier is empty, and the row
takes the *permissive* unqualified branch instead of the owner check. Proven
with identical citation text differing only in where the line broke:
single-line wrong-owner → 1 MISS; the same text reflowed → **0 MISS**. There is
not even a counter signal, because `sort -u` collapses the row into the
unqualified rows already present.

Two instances were live: `commands/plan-review.md:93-94` and
`commands/compound-refresh.md:160-161`.

This is round 1's lesson recurring one level down: the three qualified controls
were all single-line, so all three exercised the same reachable branch — the
defect round-1 finding #2 diagnosed, now in the branch its fix opened up.

*The dropped limit:* the pre-`98e66be` script carried two stated limits. Round
1 finding #4 moved "scope and limits" to §9f. Only the ambiguity one arrived.
The second — a qualifier not adjacent to its anchor reads as unqualified,
downgrading a wrong-owner MISS to a pass — landed in no file:
`git log -S "not adjacent to its anchor"` shows it added at `b927f6f` and
removed at `98e66be`, present nowhere after. A consolidation that *loses*
content, in the PR about consolidation, one commit after flagging the
duplication. And the deleted sentence was wrong in the direction that mattered:
it claimed "no live instance of that shape" while two existed.

**Fix (three parts, all applied):** restore the limit to §9f's does-NOT-cover
table stated in the line-wrap form that is provably real rather than the
contrived form the deleted note used; reflow both live citations onto one line
— verified: a wrong owner on the reflowed `plan-review.md` citation now
produces 2 MISSes (both range endpoints), where before it produced none; and
leave a back-reference at the leg-4 comment. **Deferred:** the line-joining
collection fix itself (see finding 9's sibling in the residual shard) — it
changes what counts as one citation, which §9f says must land alone with its
own re-run.
