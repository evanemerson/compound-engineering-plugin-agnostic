### 1

- status: applied
- severity: P2
- agent: adversarial-reviewer
- category: logic-error
- confidence: 95
- action_class: mechanical
- file: plugins/cepa/scripts/brain-client.sh
- lines: 256
- title: the verb died at rc=128 with completely empty output outside a git repo

**Problem:** `_cl="$(git rev-parse ... 2>/dev/null)/../cepa.local.md"` — `git
rev-parse` exits **128** outside a work tree, `2>/dev/null` swallows the message,
and because the assignment is the last command of a `||` list it **inherits that
128**. Under `set -euo pipefail` the script died right there, before either
`_die` could run. Measured independently: **rc=128, stdout and stderr both
empty.**

So the two messages written specifically to explain this state were unreachable.
Callers *do* fail closed on 128 (verified across rc 0/1/2/3/126/127/128/130 —
every value ≥2 aborts), so this was never a PHI leak. The harm is
misdiagnosis: a bare 128 with no text reads as "the client is broken" rather
than "you are not in a git repo", which is the exact shape this repo's
`resolve-plugin-root.sh` notes and its "a 127 is a path bug, never an outage"
rule exist to prevent.

Reachable only when *both* `./cepa.local.md` is absent *and* cwd is outside a
work tree (a `$TMPDIR` invocation, a container mount, a permission-dropped
runner). Unreachable via the explicit-argument form.

**Fix:** applied. Capture the status into `_common` with `|| _common=""` so the
`_die` guards are reached, and report exit 2 with a stated reason. Verified:
rc=2 with `not in a git work tree`. **Added control `sr_nongit`** to
`check-brain-client-args.sh` — and mutation-tested it by restoring the original
silent-128 line: only `sr_nongit` failed (20/21), back to 21/21 on restore. The
case asserts the *message*, not just the status, because `expect 2` alone would
have passed on the silent form via a different code path.

### 2

- status: applied
- severity: P3
- agent: adversarial-reviewer
- category: documentation
- confidence: 90
- action_class: mechanical
- file: plugins/cepa/scripts/brain-client.sh
- lines: 247, 256
- title: comment claimed resolution "exactly as" `.env.local`, which was false

**Problem:** the comment said the verb resolves `cepa.local.md` "exactly as the
writeback call sites resolve `.env.local`". It did not. `_load_env` (line ~93)
captures the status in an `if` **and** strips `/.git` via `${common%/.git}`; this
code did neither, using a bare `/..` instead. Under
`git init --separate-git-dir` the common-dir has no `.git` component, so `/..`
lands outside the work tree and the file is missed — measured: **rc=2** on such a
repo whose `cepa.local.md` sits in the work tree.

**Fix:** applied. Adopted `_load_env`'s `${_common%/.git}` form, so a normal repo
and a linked worktree both resolve correctly (re-verified: no-arg from the repo
root and from `plugins/cepa/commands/` both resolve). The separate-gitdir case
still returns rc=2 — **recorded as a known gap rather than papered over**: it
fails *closed* (suppressed writeback, never an unscrubbed send), it is shared
with `_load_env`, and inventing untested resolution logic on a PHI gate is the
larger risk. Such a repo passes the path explicitly. Stated at the code site and
in `cepa:brain`'s Compliance section.
