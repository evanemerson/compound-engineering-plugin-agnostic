Five agents plus the researcher on a 180-line diff. **Every substantive finding
was against this branch's own new work** — the second consecutive review where
that was true, which is itself the most useful signal of the run.

### 1
- status: applied
- severity: P1
- agent: adversarial-reviewer
- category: correctness
- confidence: 85
- action_class: judgment
- file: plugins/cepa/scripts/check-health.sh
- lines: 100
- title: The population that actually breaks on 2026-09-16 is the installed copies, and cepa reported them healthy

**Problem:** A template is COPIED into the user's repo. Bumping the template
reaches nothing already installed. `check-health.sh` finds their `ci.yml`,
`setup.md` classifies it a **real gate**, and fix mode never fires because the
install step is gated on "none/deploy-only" and forbids overwriting. So every
repo that installed a template before today keeps `checkout@v4` +
`setup-python@v5` forever, and cepa's own health command tells them for 38 days
that their CI is fine. Meanwhile finding 1 of the previous run was marked
`completed` while its own Problem sentence — *"the breakage lands in the user's
repo"* — remained true. The residual's proposed observer watched
`plugins/cepa/templates/`, i.e. the population this PR had just fixed, and was
structurally blind to the broken one.

**Fix:** Added an installed-template drift check to `check-health.sh`, over the
`wf_files` it already enumerates: compare the project's `uses:` pins against the
templates the plugin currently ships. **Deliberately a drift check, not a table
of runtimes and removal dates** — that table is the design a prior review here
already rejected, goes stale by construction, and needs the network. This is
self-updating: every future template bump makes every stale install report
drift. `setup.md` now requires it be surfaced as its own condition beside the CI
classification, with `NOT CHECKED` explicitly not a pass. Tested green → red →
green plus a negative control (no workflows ⇒ no verdict, not a false OK).
**Applied.** The repair half — fix mode still cannot edit an installed
workflow — is deferred as finding 9.

**A defect in this very fix, caught by smoke-testing it against this repo:**
the first cut reported MISS on `compound-engineering` itself, because its
workflows pin `actions/checkout` to a **full SHA** — strictly better than the
template's mutable tag, and precisely the hardening the templates recommend.
The check punished the correct action. Full 40-hex pins are now exempt, with a
discriminating arm added (one pin hardened, one stale ⇒ names only the stale
one). **Stated limit, recorded at the code site rather than implied:** the
exemption is a blind spot — a SHA pinned to a node20 commit is invisible, and
resolving a SHA to its runtime needs the network this read-only script does not
use.

### 2
- status: applied
- severity: P2
- agent: adversarial-reviewer
- category: self-falsifying-rationale
- confidence: 95
- action_class: judgment
- file: plugins/cepa/templates/ci/astro.yml
- lines: 6-10
- title: The header states a selection rule the six pins beside it do not follow

**Problem:** The header asserted *"Action majors are chosen by RUNTIME, not
recency"*, and the residual named that written constraint as **the mechanism**.
Applying the stated rule upstream gives `checkout@v5` / `setup-node@v5` /
`setup-python@v6`. The pins twelve lines below were `v7/v7/v7` — the newest
major of each, which is recency, the criterion the header disclaims. A
maintainer cannot reproduce the pins from the rule, so the rule stops being
load-bearing. Same self-falsifying shape CLAUDE.md records from PR #26.

**Fix:** Stated the criterion actually applied — newest major on a current
runtime, so the next forced bump is farthest out — and named the
minimum-satisfying set explicitly so the trade is visible. **Applied.** Note the
obvious counter-proposal was also wrong: a uniform `v5` leaves `setup-python` on
node20.

### 3
- status: applied
- severity: P2
- agent: adversarial-reviewer, silent-failure-hunter
- category: silent-pass
- confidence: 95
- action_class: corroborated
- file: plugins/cepa/templates/ci/astro.yml
- lines: 12-13
- title: The prescribed lookup returns a confident exit-0 wrong answer

**Problem:** Reproduced live. For `owner/repo/subpath@tag`, substituting
`<OWNER>/<ACTION>` reads the **repo root**: `github/codeql-action` returns
`using: 'composite'`, exit 0 — while the action actually referenced,
`codeql-action/init@v3`, is **node20**. And `using: composite` is not an answer
at all, since a composite's `steps:` may call node20 actions. Empty output on a
404 or auth failure was likewise being presented as a clean result. A user
following the instruction records "verified node24" and ships the dying runtime
— via the one procedure the header exists to prevent that outcome. A lying
success path shipped as guidance into other people's repos.

**Fix:** Recipe now takes `<OWNER>/<REPO>/<SUBPATH/>`, uses `base64 --decode`
for portability, and the header names all three failure modes explicitly: empty
means the request failed, `composite` is not a pass, subpath belongs in the
contents path. **Applied.**
