### 1
status: applied
severity: P1

confidence: 98
action_class: judgment
file: plugins/cepa/scripts/brain-client.sh
lines: 328-340
title: A marker count detects deletion only, so PHI added alongside intact markers passes the gate

**Problem:** `scrub-verify` compared only a floor count of `REDACTED-PHI`
occurrences and failed when it FELL. The threat model is an agent re-emitting
pre-scrub strings it still holds in context — and it can do that by ADDING them
while every sealed marker stays put. Measured:

```
sealed   {"a":"[REDACTED-PHI-SSN]","b":"[REDACTED-PHI-ID]"}        -> 2
re-Write {...same two...,"c":"SSN 987-65-4321 MRN 4567890"}        -> 2
verdict  verified: 2 redaction markers intact (sealed 2)  rc=0
```

Raw PHI posts with the gate green. Found independently by two agents. This is
the exact egress path the PR exists to close.

**Fix:** Added `_phi_fingerprint` — canonical-JSON SHA-256 over the payload
with the two authorized-mutable fields (`idempotency_key`, `source_refs`)
removed. Any byte changed outside them moves the hash. Canonical rather than
raw bytes deliberately: the agent rewrites the whole file, so key order and
whitespace legitimately change; a byte hash would suppress every honest run.
Control `sv_added` pins it; mutation-tested.

### 2
status: applied
severity: P1
agent: adversarial-reviewer
category: phi-egress
confidence: 95
action_class: judgment
file: plugins/cepa/scripts/brain-client.sh
lines: 455-470
title: Re-running the setup block laundered contamination into a passing gate

**Problem:** `scrub-seal` re-derived the seal from whatever the payload then
held. Re-running the setup block after the re-Write therefore agreed with the
contaminated bytes: seal 2 → contaminate → re-seal 0 → `0 >= 0` → pass, PHI
sent. Re-running a setup block is an ordinary recovery move (after an error, or
to recompute an idkey) and nothing in `compound.md` says it is once-only. The
stale-seal `rm -f` — correct for residual 2a's reused-path shape — is what made
re-sealing always succeed and always self-agree.

**Fix:** `scrub-seal` now refuses when a seal already exists describing
different content, comparing fingerprints (the count is what the laundering
moved). An identical-bytes re-seal stays a permitted no-op, so a plain retry is
not turned into a dead run. Controls `ss_reseal` and `ss_reseal_ok` pin both
directions; mutation-tested.

### 3
status: applied
severity: P1
agent: adversarial-reviewer
category: unevaluable-reads-as-pass
confidence: 95
action_class: judgment
file: plugins/cepa/scripts/brain-client.sh
lines: 497-534
title: A seal count of 2^63 fell through the comparison to the success branch

**Problem:** The all-digits validation accepts values `test(1)` cannot parse.
Bash `test` errors on integers ≥ 2^63, and because the failing `[` was an `if`
CONDITION, `set -e` does not fire — execution fell straight through to the
success `printf`. Measured with `9223372036854775808`: bash printed `[: integer
expression expected` and the verb exited **0** on a fully contaminated payload.
`2^63-1` compares correctly, so the boundary is exact. This is the diff's own
"an unevaluable gate must never read as a pass" rule surviving in a new
spelling, one guard below the non-numeric case that handles it correctly.

**Fix:** A magnitude guard (≤ 9 digits, far above any real marker count), AND
both comparisons inverted to state the pass explicitly (`[ ok ] || _die`) so an
unparseable comparison lands in the refuse branch rather than meaning "no
failure branch fired". Control `sv_hugeseal` pins it; mutation-tested.

title: grep -c counts lines, so a dropped marker on a shared line was invisible

**Problem:** `compound.md` emits single-line JSON. `grep -c` counts matching

dropping one of two markers left it unchanged. Measured: a two-marker line

**Fix:** One shared `_phi_count` using `grep -o | grep -c ''`, so seal and
verify cannot drift apart. Controls `sv_oneline` (single line) and the
multi-line case pin it. Its own control was initially green for the wrong
reason — see finding 9.

title: $P is agent-chosen, so concurrent runs collide on both payload and seal

**Problem:** `P="<payload-file you just wrote>"` with no `mktemp` and no run
id. Two agents reading the same instructions plausibly pick the same name.
Measured both directions: run A seals 1, run B overwrites with 3, A verifies

also `rm -f`s the other run's payload mid-flight.

**Fix:** Derive the path in the setup block (`mktemp`) and have the later block
re-read it from one recorded location — the path itself then crosses the block
boundary, so it goes through the filesystem per 2g. Deferred: a contract change
to `compound.md`'s payload convention touching every step that names `$P`,
worth its own reviewable diff. **Filed as residual 2j.**

**Problem:** `sv_oneline` hardcoded its seal as `2`. Under a line-counting
