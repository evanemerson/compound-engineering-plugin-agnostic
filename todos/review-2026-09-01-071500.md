### 1

severity: P1

category: correctness
confidence: 100
action_class: corroborated
file: plugins/cepa/commands/handoff.md
lines: 176-195
title: Merged branch with post-merge commits — `-D` destroys unmerged work

**Problem:** The `Merged` test was "gh reports MERGED", a set-membership
check. Merge a PR, then keep working on the branch — `gh` still truthfully
says MERGED because the PR *was* merged. Reproduced: branch carried 3
commits absent from trunk, `git branch -D` deleted it with exit 0, no
warning, recovery reflog-only. A merged PR is not a merged branch.

**Fix:** `Merged` now requires four conjunctive conditions; condition 3 is
`git rev-parse <branch> == headRefOid` from the PR. Any condition failing
means `Unknown`, which emits no deletion.

### 2
status: completed
severity: P1
agent: adversarial-reviewer
category: correctness
confidence: 100
action_class: corroborated
file: plugins/cepa/commands/handoff.md
lines: 698-716
title: Failed `checkout -b` does not stop the following `-D`

**Problem:** The safety argument claimed git enforces checkout-before-delete.
It only does so when HEAD is on the branch being deleted. Reproduced with
HEAD on `main` and a name collision: `checkout -b` exits 128, the next
`git branch -D` deletes an unmerged branch anyway, exit 0. The emitted block
was three newline-separated lines, not a chain.

**Fix:** the block is now `set -e` with a `git rev-parse --verify` proving
the checkout succeeded before the delete. Reason (1) is restated as a narrow
guard, explicitly "do not lean on it".

### 3

action_class: corroborated
file: plugins/cepa/commands/handoff.md
lines: 178-190
title: Multiple PRs per head branch, and non-trunk merge bases, unhandled

**Problem:** "reports MERGED" over an unordered list with no tie-break.
Confirmed live in this repo: `feat/sibling-batch-exemption` has PR #22
MERGED into `main` and PR #21 CLOSED into a *sibling branch*. The dangerous
inversion — an old PR merged into a deleted stacking base while a newer PR
is still open — would fire the rule and delete the open PR's work. The
merge base was never compared to the resolved trunk.

**Fix:** conditions 1 and 2 — exactly one MERGED PR, and its `baseRefName`
must equal the resolved trunk. Any open PR on the same head means `Unknown`.

## Self-caught during fix verification

The first fix for finding 1 used `git rev-list --count <mergeCommit>..<branch> == 0`.
The verification suite caught it as a false positive: a **squash** merge
creates a commit with no parent link to the branch, so the tip is never an
ancestor and the count is >=1 for *every* squash-merged branch. That rule
would have classified all merged branches `Unknown` and deleted nothing,
ever. Replaced with `headRefOid` equality and both directions re-verified.

This is the same trap the `git cherry` rule warns about, met a second time —
on a squash repo, ancestry does not survive the merge.
