**Correction (2026-09-25, same day).** This file originally claimed that
frontmatter had "drifted from what `review.md` documents" — that
`code-simplifier` no longer pinned `opus` and all five companions were
`inherit` or absent. **That claim was false.** `review.md:465` is accurate:
`code-simplifier` pins `model: opus`, the other four ship `inherit`. Verified
across both on-disk plugin trees (`plugins/cache/…` and
`plugins/marketplaces/…`), which agree exactly.

The false reading came from the verification command, not the plugin. It was
`sed -n '1,12p' <file> | grep -iE '^model:'` — a fixed 12-line window.
`code-simplifier`'s `model:` field sits at **line 40**, because its
`description:` is a multi-line block holding three `<example>` blocks; the
frontmatter does not close until line 41. The grep found nothing and the
absence was read as "no `model:` field" rather than as "looked in the wrong
place."

**Lesson — parse frontmatter as frontmatter.** A fixed line window is not a
frontmatter reader. Delimit on the `---` fences instead:
`awk '/^---$/{n++; next} n==1' <file> | grep -E '^model:'`. A negative result
from a truncated window is indistinguishable from a real absence, which is
exactly the silent-pass class this repo's Active roster exists to catch — here
it produced a false *finding* rather than a false clean pass.

title: "\"never point a link at a slug carrying a bare integer\" forbids stable headings the rule does not mean to cover"

**Problem:** The rule's prescription generalized from "a count" to "a bare
integer," which is a strictly larger set. Verified against GitHub's slug
algorithm: `## Step 3` → `#step-3`, `## Django 5.2` → `#django-52`,
`## Agent 1` → `#agent-1`. None of those drift — an ordinal or a version is
fixed once written — yet all carry bare integers and would be forbidden as
written. This repo is full of them: `plugins/cepa/commands/compound.md` alone
has `## Step 1` through `## Step 5` and `## Agent 1` through `## Agent 5`. A
rule in an always-loaded instructions file that misfires on legitimate headings
trains every future session to make the wrong edit.

**Fix:** Applied. Narrowed the prescription to "Drop counts from headings that
are link targets," and added a paragraph drawing the count-vs-digit distinction
explicitly, with the `## Step 3` and `## Django 5.2` counter-examples and a
test that does not depend on spotting digits: *would this number have to be
edited if the repo grew?*
