- title: Weekly files hijack triage's "most recent review-*.md" selection and silently shadow untriaged PR findings

**Problem:**
`triage.md:19` selects *"the most recent `review-*.md` file (by filename date,
or use the most recently modified)"* — a single-file selection, not a scan.
`review.md:355-357` deliberately keeps the `review-` prefix so
*"existing consumers that glob `review-*` keep matching it"* — reasoning about
the benefit without checking what the glob-based consumer does with a match.

Lexicographically, the character after `review-` decides: a digit (0x30–0x39)
always sorts before `w` (0x77). So `review-weekly-*` sorts **after every**
`review-<digits>-*` filename, permanently, regardless of actual date. It also
wins any mtime tiebreak while it is newest.

And by construction it contains **zero** `status: pending` findings
(`review.md:362`).

Concrete failure: dev runs `/cepa:review` Friday → 9 pending findings in
`review-2026-07-24-*.md`. Sunday cron → `review-weekly-2026-07-26-*.md`, all
deferred. Monday `/cepa:triage` selects the weekly file, finds 0 pending,
reports *"no pending findings"* and stops (`triage.md:23`). Friday's P1s are
never triaged, and the run reports as a clean triage. This is a live
regression to a previously-correct command.

**Fix:**
Amend `triage.md` Step 1 in this PR: skip files whose `scope:` begins
`weekly:` when selecting, or select the most recent file containing at least
one `pending` finding. Either way triage must **name the file it loaded** in
its report so "0 pending" is attributable.

These become indistinguishable from each other and from a healthy quiet week:
- A typo'd heading (`## Review Agents (weekly)`) → "absent" → fail-closes every

fix on someone else's PR.

agent's Setup step 1 (fixes Leg A). Filing to `memory/tasks.md` per finding 9

Step 1 rules 1-4, where on clean main `git diff main...HEAD` is empty →
"no changes found to review," a clean-pass report for an unreviewed window.

**Fix:**
Name the third exit. Specify the root-commit fallback explicitly, and specify
that any failure of the scope commands exits with a named reason rather than
falling through to Step 1's PR/branch rules — the fall-through is what turns a
hard error into a clean pass.
