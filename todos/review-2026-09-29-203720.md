**Problem:**
The rewritten lead paragraph says the `-`, the bold markers, and the case "are
all optional, and the pattern must tolerate **every combination**." The shipped
pattern does not. Reproduced against the shipped regex — 3 of 9 fixture lines
matched:

```
  - status: indented      -> NO MATCH   (whitespace BEFORE the dash; the pattern
                                         is ^-?[[:space:]]* — dash first, space
                                         after, so indentation breaks the anchor)
* status: star            -> NO MATCH   (markdown allows * and + as list markers)
+ status: plus            -> NO MATCH
- *status:* italic        -> NO MATCH   (single-asterisk; the group is (\*\*|`))
- __status:__ underscore  -> NO MATCH   (underscore-bold is valid markdown)
- status : spaced         -> NO MATCH   (space before the colon)
```

The indentation case is the same failure shape as this PR's own root cause, one
level deeper. None of the five is named in the four load-bearing bullets, the
mid-line paragraph, or the three NOT-tallyable shapes — so a reader who trusts
"every combination" gets a silent zero with no warning.

**Scope limit, verified:** all five have **zero occurrences** in the real
193-file corpus (`grep -rlE` per spelling → 0 each). This is latent risk in a
contract file, not an active miscount — which is why it is P2 and `judgment`
rather than P1.

**Related asymmetry, observed live in this very findings file.** Because
`[[:space:]]*` sits *after* the optional dash, an indented `status:` with **no**
dash DOES match, while an indented `- status:` with a dash does not:

```
  status: fresh        -> MATCHES     (frontmatter, brain: block — not a finding)
  - status: applied    -> NO MATCH    (nested list item — IS a finding)
```

Running the shipped pattern on this file returns 5 status rows against 4 `### N`
headings, because it reached into the `brain:` frontmatter block. The over-match
is benign here (a Run Metadata block is not a finding, and the discrepancy is
visible), but the direction is backwards: the pattern reaches non-findings in
frontmatter while missing real nested findings. Any fix to the anchor should
close both halves, and the `### N` comparison the section prescribes is what
surfaces it — worth stating as the reason that comparison is mandatory.

**Fix:**
Either tighten the claim or widen the pattern — do not leave them disagreeing.
Cheapest correct option is to replace "every combination" with a claim that
matches the regex, and name the unhandled spellings as out of scope:

> The leading `-`, the bold markers, and the field's case are all optional.
> Out of scope, and a silent zero if they appear: indented (nested) list items,
> `*`/`+` list markers, single-asterisk italic, `__underscore-bold__`, and a
> space before the colon. None occurs in any known corpus; widen the pattern if
> one ever does.

If widening instead, `^[[:space:]]*[-*+]?[[:space:]]*` handles indentation and
markers; re-run the corpus sweep afterward per this section's own rule.

- title: `[a-z]+` truncates at the first non-letter, collapsing two statuses into one uniq bucket

**Problem:**
`grep -o` prints only the matched text, and the value class `[a-z]+` stops at
the first non-letter. Two distinct hyphenated statuses therefore truncate to the
same string and merge into a single `uniq -c` row. Reproduced:

```
$ printf -- '- status: not-attempted\n- status: not-configured\n' | grep -oiE '<pattern>' | sort | uniq -c
      2 - status: not          # two DIFFERENT statuses, one bucket
```

Both values are real — `status: not-attempted` and `status: not-configured` both
occur in the live corpus (also `resolved-as`). The bullet at 243-249 discusses
`uniq -c` bucketing by *spelling* but never mentions truncation, so a reader
comparing per-row counts against a per-status expectation gets a wrong answer
with no signal.

**Verified scope limit:** no single corpus file contains two same-prefix values
today, so the collapse is not currently triggered. And the **row total stays
correct** (3 findings → 3 rows, confirmed), so the section's own prescribed
check — row total vs `### N` headings — is unaffected. That is what holds this
at P2 rather than P1.

**Fix:**
Add one clause to the existing `-o`/`uniq -c` note at 243-249:

> `[a-z]+` also stops at the first non-letter, so `not-attempted` and
> `not-configured` both print as `status: not` and share one bucket. The row
> **total** is still correct — which is why the total, not the breakdown, is the
> oracle.

Optionally widen the value class to `[a-z-]+` / `[a-z_-]+`; the row total is
unaffected either way.
