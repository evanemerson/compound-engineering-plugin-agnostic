**Problem:**

matched:

```

* status: star            -> NO MATCH   (markdown allows * and + as list markers)
+ status: plus            -> NO MATCH
- *status:* italic        -> NO MATCH   (single-asterisk; the group is (\*\*|`))
- __status:__ underscore  -> NO MATCH   (underscore-bold is valid markdown)
- status : spaced         -> NO MATCH   (space before the colon)
```

The indentation case is the same failure shape as this PR's own root cause, one
level deeper. None of the five is named in the four load-bearing bullets, the
mid-line paragraph, or the three NOT-tallyable shapes — so a reader who trusts
"every combination" gets a silent zero with no warning.

**Original scope estimate — WRONG, corrected while applying.** The finding as
filed said all five spellings have "zero occurrences in the real 193-file
corpus," so the risk was latent. That was measured with the wrong probe: it
tested for indented `- status:` (**with** a marker), which is indeed absent.
The live form is indented `status:` with **no marker** — YAML list-item findings
(`- id: 1` followed by indented fields) — and it occurs in **50 of 193 files**.
So the indentation half of this finding was **active, not latent**, and the most
common non-obvious spelling in the corpus.

**The filed fix was also wrong, and applying it verbatim caused a regression.**
It proposed excluding frontmatter by requiring a list marker on indented lines.
Measured: that candidate passed a 13-case fixture and then **lost rows on 51 of
193 corpus files, 17 of them dropping to zero** — including one file going 26 →
0. Exactly the defect class this section exists to prevent, produced by the
section's own suggested remedy.

Root cause of the bad advice: an indented `status: applied` inside a finding and
an indented `status: fresh` inside a `brain:` frontmatter block are
**byte-identical**. No anchor can separate them, so the "over-match" this finding
originally reported is not fixable by pattern — it is inherent, and the `### N`
comparison is the only thing that catches it.

**Fix — APPLIED:**
Widened both patterns to `^[[:space:]]*[-*+]?[[:space:]]*` (indentation before an
optional marker) with the emphasis group extended to `(\*\*|__|\*|_|`)?` and
`status[[:space:]]*:` to allow a space before the colon. The lead paragraph now
carries a table of all six live spellings including indented-no-marker with its
50/193 measurement, and a new bullet explains why requiring a marker on indented
lines is the wrong fix, citing the 51-file regression.

- title: `[a-z]+` truncates at the first non-letter, collapsing two statuses into one uniq bucket

**Problem:**
`grep -o` prints only the matched text, and the value class `[a-z]+` stops at
the first non-letter. Two distinct hyphenated statuses therefore truncate to the
same string and merge into a single `uniq -c` row. Reproduced:

```
$ printf -- '- status: not-attempted\n- status: not-configured\n' | grep -oiE '<pattern>' | sort | uniq -c
      2 - status: not          # two DIFFERENT statuses, one bucket
```

Both values are real — `status: not-attempted` and `status: not-configured` both
occur in the live corpus (also `resolved-as`). The bullet at 243-249 discusses
`uniq -c` bucketing by *spelling* but never mentions truncation, so a reader
comparing per-row counts against a per-status expectation gets a wrong answer
with no signal.

**Verified scope limit:** no single corpus file contains two same-prefix values
today, so the collapse is not currently triggered. And the **row total stays
correct** (3 findings → 3 rows, confirmed), so the section's own prescribed
check — row total vs `### N` headings — is unaffected. That is what holds this
at P2 rather than P1.

**Fix — APPLIED:**
Widened the value class to `[a-z_-]+` so hyphenated and underscored values no
longer truncate, and promoted the `uniq -c` note out of the `-i` bullet into its
own paragraph ("Read the row total, not the per-row counts") covering **both**
bucketing failures — one status across several rows, and two statuses collapsed
into one row — and stating plainly that neither affects the row total, which is
the only figure the `### N` comparison needs.

Verified: `not-attempted` and `not-configured` now print in full as distinct rows;
corpus regression 0 losses.
