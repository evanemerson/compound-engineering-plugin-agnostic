- title: Bare anchor followed by a hyphen and digits parses as a bogus range, failing the merge gate on ordinary prose

**Problem:**
Widening the range tail from `-[0-9]+[A-Za-z]+` to `-[0-9]+[A-Za-z]*` made the
letter optional at EVERY hyphen-joined segment, not only at the anchor. Any
bare `§N` immediately followed by a hyphen and digits — a year, a day, a count
— now parses as a two-anchor range, and the phantom second anchor resolves to
nothing.

Reproduced independently on a clean copy of this branch:

```
$ printf '\nAs discussed in the §7-2026 planning cycle, nothing special.\n' >> README.md
$ bash scripts/check-model-pins.sh
MISS model-pin: §2026 is cited but no plugins/*/skills/*/SKILL.md has a '## 2026.' heading
-- 1 MISS, 0 WARN --
```

`§9-14` and `§8-30` behave the same. This repo dates everything `YYYY-MM-DD`
and writes `§7` constantly, so `§7-2026` is a plausible sentence. The failure
message names `§2026`, which appears nowhere in the author's text — so the
error gives no clue what went wrong.

The inline comment at lines 497-502 justifies the widening by noting the seven
live hyphenated-English shapes have no digit after the hyphen. That argument
only covers the letter-after-hyphen case (`§5-style`); it says nothing about
the digit-after-hyphen case the same edit opened. The safety claim is
incomplete.

This is the same shape as the defect the PR was written to fix: a regex
widened without fully re-deriving what it now accepts.

**Fix:**
Require a letter on every range tail — `(-[0-9]+[A-Za-z]+)*`, which is the
pre-PR tail. Validated on a sandboxed copy: `§7-2026` truncates to `§7`,
coverage stays at 110 pairs, and `§9c-9q` still MISSes on its second endpoint
(so control cases 13/14 stay green). The only real range in the repo is
`§9c-9d`, which the fix preserves — ranges here are always lettered.
Add a control planting the digit-tail shape and asserting 0 MISS.

- title: An ordinary numbered procedure in any skill silently registers policy anchors and disarms the wrong-owner check

**Problem:**
The index now accepts `## N.` headings with no owning-skill restriction.
`### 9c.` is a shape nobody writes by accident; `## 1.` is a shape ordinary
numbered-step documentation writes constantly. So any skill that adds a
numbered procedure registers itself as an owner of those anchor numbers, and
the qualified branch then resolves a wrong-owner citation against it.

Reproduced independently, both directions on identical trees:

```
# wrong-owner citation, no extra headings (control):
MISS model-pin: §3 is cited as `grounding` §3 but grounding/SKILL.md has no '## 3.' heading
-- 1 MISS, 0 WARN --

# after adding "## 1. Check availability", "## 2. Invoke", "## 3. Sanitize"
# to plugins/cepa/skills/grounding/SKILL.md:
INFO section citations checked: 111 distinct pairs ...; 16 anchors defined by 8 skill files
-- 0 MISS, 0 WARN --
```

The dangerous detail: `anchors defined` stays at **16** either way, because
autonomy already owns 1/2/3. There is no INFO delta, so the coverage loss is
invisible in the diff and in the log.

§9f's does-NOT-cover row says "zero instances today — only this file defines
numbered sections at either heading level." That premise was cheap to hold
when only `### N<letter>.` counted. The widening makes one ordinary
contribution break it.

**Fix:**
A design call, hence `judgment`. Options: (a) restrict the level-2 arm to the
skill that owns policy anchors; (b) reject a level-2 heading in a skill that
defines no level-3 lettered anchors; (c) make a second owner registering an
already-owned anchor a MISS, turning a silent collision into the loud failure
this leg exists to produce. (c) is the most in keeping with the checker's
stated philosophy.
