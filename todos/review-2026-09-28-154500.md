# Review — PR #73 `chore/plugin-install-freshness-check`

A checker that warns when the cepa plugin copy Claude Code LOADS lags `main`.

**The headline result:** two P1s, both in the new checker itself, both of the
exact class the checker exists to prevent — a detector printing a confident
sentence about something it did not actually verify. Both were found by
*running* the code, not reading it, and both were independently reproduced
before being fixed. This is the fourth consecutive instance of
`docs/solutions/logic-errors/a-detector-is-not-exempt-from-the-class-it-detects.md`
on this repo's tooling surface.

---

### 1

- status: applied
- severity: P1
- agent: silent-failure-hunter
- category: logic-error
- confidence: 95
- action_class: mechanical
- file: scripts/check-plugin-freshness.sh
- lines: 107
- title: hop 1 reports a git ERROR as "is BEHIND"

**Problem:** `git merge-base --is-ancestor` has three outcomes: 0 ancestor, 1
not-ancestor, **128 error** (bad object, not a repo, corrupt clone). The
`if`/`else` collapsed 1 and 128 into the same arm, so a clone that could not
answer the question at all printed the confident sentence
`WARN marketplace clone is BEHIND`. Reproduced directly: `merge-base
--is-ancestor <sha-from-another-repo> HEAD` returns 128. Hop 2's parallel call
at line 167 was already guarded by a preceding `cat-file -e`; the asymmetry
between the two sites was the defect. A false alarm here is worse than silence —
it teaches the operator to ignore the one check that tells them a security fix
is not running.

**Fix:** applied. Resolve the clone's HEAD and verify `REF_SHA` is a present
object *before* asking about ancestry, mirroring hop 2's guard. A clone missing
the object now reports `UNKNOWN ... hop 1 unverified`, and a clone with no
resolvable HEAD reports its own distinct UNKNOWN. Verified: foreign clone →
UNKNOWN at rc=0; genuinely stale clone → still WARN with a correct count.

### 2

- status: applied
- severity: P1
- agent: silent-failure-hunter
- category: logic-error
- confidence: 95
- action_class: mechanical
- file: scripts/check-plugin-freshness.sh
- lines: 111-112
- title: the `|| echo '?'` count fallback can never fire

**Problem:** the BEHIND count inlined `$(git -C "$MARKET" rev-parse HEAD)`
**unquoted** as a `--not` operand. When that inner call failed it expanded to
nothing, leaving the still-valid command
`git rev-list --count <sha> --not -- plugins/`, which exits 0 and prints a
real-looking total — so `|| echo '?'` could never fire on the failure it was
written for. Reproduced directly: it printed `66`. This is Detection signal
S1/S2 from `a-detector-is-not-exempt-from-the-class-it-detects.md` — an
unguarded command substitution whose failure silently changes the meaning of
the command it feeds instead of surfacing as an error.

**Fix:** applied. HEAD is resolved into `CLONE_HEAD_FULL` in the guard above
and the count uses that quoted variable; if resolution fails the whole hop
reports UNKNOWN rather than reaching the count at all.

### 4

- status: applied
- severity: P2
- agent: architecture-reviewer
- category: architecture
- confidence: 55
- action_class: judgment
- file: plugins/cepa/commands/setup.md
- lines: 119-142
- title: check 4 had no stated behavior for a non-cepa repo

**Problem:** `setup.md` Step 1 exists so the command runs identically in any
project by resolving shipped scripts through `$CEPA_ROOT`. Check 4's new
paragraph broke that pattern with a bare repo-root-relative path gated on the
prose condition "when running in the cepa repo itself" — a judgment nothing
else in the command asks the agent to make, and with no instruction at all for
the (overwhelmingly common) case of a different project. An agent told to
"prefer the freshness check" in a repo that has no such script has undefined
behavior, which in practice means it either invents a path or silently skips.

**Fix:** applied. Replaced the prose condition with an explicit existence test
and an `else` arm that names the fallback out loud ("freshness check
unavailable — not the cepa source repo"), plus a rule that an absent script is
an unverified answer rather than a pass. A comment states why this one script
is deliberately NOT resolved through `$CEPA_ROOT`: it is repo tooling, not
shipped plugin content.

### 5

- status: applied
- severity: P3
- agent: security-sentinel
- category: robustness
- confidence: 85
- action_class: mechanical
- file: scripts/check-plugin-freshness.sh
- lines: 151
- title: `read -r INST_VER INST_SHA` desyncs on a value containing a space

**Problem:** `read -r a b` splits on IFS whitespace, so a version string
containing a space shifts part of itself into the SHA variable. Reproduced:
`"1.26.5 evil"` yielded `INST_VER=1.26.5`, `INST_SHA="evil abc123"`. The values
come from `installed_plugins.json`, written by the Claude Code runtime rather
than by this repo, so their shape is not ours to assume. Downstream `git` calls
fail safely on the garbage token, so this degraded to a wrong verdict, never to
code execution.

**Fix:** applied. python3 now emits **tab**-separated fields and strips
whitespace from each, and the shell reads with `IFS=$'\t'`. Verified: a
space-bearing version stays wholly in the version field and the SHA still
resolves and compares correctly.

### 6

- status: applied
- severity: P3
- agent: security-sentinel
- category: robustness
- confidence: 80
- action_class: mechanical
- file: scripts/check-plugin-freshness.sh
- lines: 165-170
- title: a dash-leading SHA reaches `git` as an option

**Problem:** `INST_SHA` was interpolated into `git cat-file -e`,
`git merge-base --is-ancestor`, and `git log` as a bare revision token. A value
beginning with `-` is parsed as an **option**, not a revision — confirmed exit
129. No destructive option is reachable through these three read-only
subcommands in this shape, so this is hardening rather than an exploitable
path.

**Fix:** applied. The SHA is shape-checked against `^[0-9a-fA-F]{7,40}$` before
any git use. Crucially the reject is reported as its own UNKNOWN rather than
rewritten to the `-` sentinel: collapsing garbage into "none recorded" would
make a corrupt record indistinguishable from an absent one and let the
version-compare fallback print a confident verdict off a field it had silently
discarded. Verified: `--upload-pack=evil` → UNKNOWN at rc=0.

### 7

- status: applied
- severity: P3
- agent: silent-failure-hunter
- category: logic-error
- confidence: 70
- action_class: mechanical
- file: scripts/check-plugin-freshness.sh
- lines: 151-165
- title: python3 dying outside its try/except printed a garbled `v ` line

**Problem:** the old form read a process substitution's stdout without checking
python3's exit status. If python3 died outside its own `try/except` (kill, OOM,
SIGPIPE) both variables landed empty, fell into the wildcard `case` arm, and
printed `INFO loaded copy: v (cache .../)` — a data-shaped line describing
nothing — before eventually reaching UNKNOWN.

**Fix:** applied. Output is captured into `INST_RAW` with an explicit
`if ! INST_RAW=$(...)` exit-status check, and an empty `INST_VER` now has its
own `case` arm that reports UNKNOWN instead of falling through to the compare.
Verified: an empty-string version no longer produces a bare `v` claim.
