### 1
status: pending
severity: P1
agent: silent-failure-hunter, adversarial-reviewer
category: silent-failure
confidence: 100
action_class: corroborated
file: .github/workflows/changelog.yml
lines: 82-85
title: git diff --quiet reports "already current" for an untracked file, so a missing CHANGELOG.md is never regenerated and the job stays green forever

**Problem:** `git diff` compares the worktree against the **index**. An
untracked file has no index entry, so `git diff --quiet -- CHANGELOG.md` exits
**0** — the identical exit code to "already current". If `CHANGELOG.md` is ever
absent from `main` (a revert that overshoots, a `git rm`, a bad rebase, or this
workflow being lifted into another repo), then on every subsequent release the
job checks out `main`, generates a complete and correct 243-line file, reads the
gate as "already current", logs `CHANGELOG.md is already current; nothing to
commit`, and exits 0. Nothing is pushed. The log line asserts the exact opposite
of the truth, and the condition never self-heals because each run re-derives the
same wrong conclusion.

Both agents reproduced it end-to-end against a real bare remote. Orchestrator
verification confirms the primitive independently: on an untracked file
`git diff --quiet` exits 0; after `git add --intent-to-add` it exits 1.

This is the failure class the file's own comment at lines 99-101 claims to
prevent — "a workflow that exhausts its retries and exits 0 is indistinguishable
from one that had nothing to do" — reached through a different door. It matches
signal 1 of `docs/solutions/logic-errors/autonomous-gates-must-fail-closed-on-missing-artifacts.md`
exactly: a gate phrased "proceed when no diff in `<file>`" with no existence
check on the file itself.

Severity note: silent-failure-hunter rated this P1, adversarial-reviewer P2 (the
lost artifact is derived, and one manual commit restores it). Filed P1 because
the defect is self-perpetuating, produces a green check over a wrong result, and
this repo names the silent pass as its dominant defect class.

**Fix:** assert the artifact exists, and use a comparison that sees untracked
files:

```bash
[ -f CHANGELOG.md ] || { echo "::error::generator exited 0 but CHANGELOG.md does not exist"; exit 1; }
git add CHANGELOG.md
if git diff --cached --quiet -- CHANGELOG.md; then
  echo "CHANGELOG.md is already current; nothing to commit"; exit 0
fi
```

### 2
status: pending
severity: P1
agent: silent-failure-hunter, adversarial-reviewer
category: correctness
confidence: 100
action_class: corroborated
file: scripts/generate-changelog.sh
lines: 100
title: A release with an empty title collapses the TSV row — the base64 body lands in the heading link, every bullet is lost, and the result auto-commits to main

**Problem:** Tab is an **IFS whitespace** character, so with `IFS=$'\t'`, `read`
collapses runs of tabs into one delimiter. Empty TSV fields do not survive the
split. Line 60 emits `(.name // "")`, so a release with a blank title produces
`tag⇥created⇥⇥url⇥b64`; the doubled tab collapses and every field shifts left:
`name`←`html_url`, `url`←the base64 body, `b64`←empty.

Downstream, line 106 emits a heading whose link target is a multi-hundred-character
base64 blob; the empty `b64` decodes to an empty body so line 132 writes
`_No PR-derived entries; see the release page._`, losing every PR entry for that
release; and lines 112-118 accidentally suppress the italic lead (because
`lead == name`, so the `!=` guard fails), removing the last visual cue that
anything shifted. The 12-line floor passes, the script exits 0 and reports
`wrote ... - N releases`, and the workflow commits the corrupted file to `main`
with no human in the loop.

Orchestrator verification reproduced the primitive directly: with
`printf 'v1.0.0\t2026-01-01\t\thttps://example/url\tQkFTRTY0'`, `read` yields
`name=[https://example/url]`, `url=[QkFTRTY0]`, `b64=[]`.

Latent today — all 28 published releases have non-empty names — but clearing a
title in the GitHub UI is a two-click operation, `gh release create` without
`--title` yields a null name, and the workflow triggers on `edited`.

**Fix:** stop relying on `read` for TSV, or guarantee the field is never empty.
Either parse positionally in a way that does not collapse, or add a
field-integrity assertion that fails loudly:

```bash
awk -F'\t' 'NF!=5 {exit 1}' "$FEED" || { printf 'FATAL: malformed release row\n' >&2; exit 1; }
```

plus a guard in `emit` rejecting a `url` that does not match `^https://`, so a
shifted row fails rather than commits.

### 3
status: pending
severity: P2
agent: adversarial-reviewer, reliability-reviewer, silent-failure-hunter
category: silent-failure
confidence: 95
action_class: corroborated
file: scripts/generate-changelog.sh
lines: 26-27, 103
title: base64 decode failure silently guts every entry, base64 is missing from the dependency check, and the sanity floor cannot catch it

**Problem:** `body=$(printf '%s' "$b64" | base64 -d 2>/dev/null) || body=''`
swallows a decode failure and discards the message. If `base64 -d` fails for
every row — a host where `base64` only accepts `-D` (older BSD/macOS), or the
field shift from finding 2 handing `b64` a URL — every release gets an empty
body, every entry degrades to `_No PR-derived entries; see the release page._`,
and the file loses 100% of its content while still clearing the 12-line floor at
~120 lines. Exit 0, confident success message, auto-committed to `main`.

Lines 26-27 check `gh` and `git` but never `base64`. The same swallow applies to
`bullets` at lines 124-127: an `awk` or `sed` failure yields an empty `bullets`,
unchecked.

Compounding the diagnosis problem, `_No PR-derived entries_` is emitted for four
distinct causes: a genuinely bulletless release, a decode failure, a body with
bullets but no `## …Changed…` heading, and finding 2's field shift. The file
cannot tell you which fired. `CHANGELOG.md:163` (v1.10.1) already carries one —
verified against the API as a legitimate instance, but establishing that took an
API call.

**Fix:** add `base64` to the dependency check; make a decode failure fatal
(capture stderr to a file rather than `/dev/null`); and give the
"body present but no matching section" case a distinct string. An empty `b64`
decodes to empty with exit 0, so a genuinely bodyless release still takes the
fallback path correctly.

### 4
status: pending
severity: P2
agent: silent-failure-hunter, adversarial-reviewer, architecture-reviewer
category: silent-failure
confidence: 95
action_class: corroborated
file: scripts/generate-changelog.sh
lines: 95, 101, 152-159, 171
title: The generator never asserts that what it wrote matches what it read, and the line-count floor it relies on has zero margin

**Problem:** `$count` is the number of rows the API returned; nothing checks
that `$count` entries were emitted, yet line 171 reports it as fact. Three
independent leaks: `mapfile -t ROWS < <(sort ...)` at line 95 does not check
`sort`'s status (a `sort` dying mid-stream yields a truncated `ROWS` with `$?`
still 0); line 101's `[ -z "$tag" ] && return 0` drops a malformed row with no
counter and no warning; and `emit`'s appends are unchecked (see finding 8).

silent-failure-hunter reproduced the partial case: with `sort` emitting 1 of 2
rows then dying, the file contains one release while the success line reports
two. The 12-line floor is worthless against it — a single surviving release
clears it at 16-18 lines, so 27 of 28 releases can vanish and still pass.

Separately, the floor itself is fragile: the header emits **exactly 12** lines
and the threshold is `-le 12` — zero margin — while the comment on line 153 says
"the header alone is ~11 lines", already off by one. Adding one header line makes
the guard unreachable even for a zero-release file, silently. In a script whose
own header argues that restated counts are the failure class it exists to
eliminate, this is a restated count.

**Fix:** replace the floor with an assertion tying output to input, which
subsumes it and needs no magic number:

```bash
emitted=$(grep -c '^## \[' "$TMP")
[ "$emitted" -eq "$count" ] || {
  printf 'FATAL: read %s releases but emitted %s entries; refusing to write %s\n' \
    "$count" "$emitted" "$OUT" >&2; exit 1; }
```

Also capture `sort`'s exit status by writing to a temp file rather than using
process substitution.

### 5
status: pending
severity: P2
agent: reliability-reviewer, silent-failure-hunter, adversarial-reviewer
category: reliability
confidence: 90
action_class: corroborated
file: .github/workflows/changelog.yml
lines: 74-97, 102
title: The retry loop retries the wrong failure, diagnoses every failure as a race, and has no backoff

**Problem:** Three defects in one construct.

*Retries the wrong thing.* The loop's shape implies three full
fetch→generate→commit→push cycles on any failure, and the generator's own
comment frames the design around that. But line 79-80's
`bash scripts/generate-changelog.sh CHANGELOG.md || { …; exit 1; }` terminates
the entire `run:` script on the first failure — not the iteration. The single
`gh api --paginate` call is the only network call, so any transient 5xx,
secondary rate limit, or dropped connection ends the job immediately with
attempts 2 and 3 never running. Retry protection covers the *less* likely
failure (a push race, already mitigated by the concurrency group) and is absent
for the more likely one.

*Misdiagnoses the cause.* Every push rejection prints
`push rejected (main moved); retrying` and the exhaustion message blames commit
velocity. Reproduced against a bare remote with a rejecting `pre-receive` hook —
standing in for branch protection, a revoked token, or an archived repo — all
three attempts printed "main moved" and the final error blamed a repo with
roughly one commit a day. Note this is the exact scenario `CLAUDE.md` already
recommends creating (turning on branch protection).

*No backoff.* Reproduced: three attempts completed in **64ms**. For the race the
loop exists to cover, all three land inside the window of the same competing
push. The loop is decorative.

**Fix:** branch on the failure mode before retrying — compare `origin/main`
after a failed push and fail loudly when it did not move (protection or token
scope, not a race) — reword the exhaustion message to name both possibilities,
add `sleep $((attempt * 5))`, and give the generation call its own bounded retry
that fails fast on unambiguously non-transient errors rather than burning three
attempts on a bad token.

title: The zero-releases guard falls through when grep exits 2

**Problem:** `grep -c .` on an empty file exits 1 but prints `0`, so the

