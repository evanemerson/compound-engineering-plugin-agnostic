# Review — PR #51 sweep merged-branch inventory

The central finding: the PR cited `/cepa:handoff`'s four safety conditions as
authoritative while prescribing a query that could not evaluate two of them.
Citing a condition is not the same as being able to check it.

### 1
status: applied
severity: P1
agent: adversarial-reviewer
category: correctness
confidence: 100
action_class: corroborated
file: plugins/cepa/commands/sweep.md
lines: 140-146
title: `--state merged` made condition 1 vacuous — open PRs structurally invisible

**Problem:** verified `gh pr list --state merged --json state --jq '[.[].state]|unique'`
returns `["MERGED"]` by construction. An OPEN PR on the same head is not
"evaluated and passed" — it is absent from the evidence. Condition 1 exists
for exactly that shape (older PR merged into a since-deleted stacking base,
newer one still open) and the merged-only query made it always-true in the
one case it was written for. Synthetic proof: head with #40 MERGED and #41
OPEN is listed by the old query, destroying #41's branch.

**Fix:** `--state all --limit 201` carrying `state`, grouped by
`headRefName`; listed only when the group holds exactly one MERGED and zero
OPEN. Same cost — 0.31s, one call.

### 2
status: applied
severity: P1
agent: adversarial-reviewer
category: correctness
confidence: 100
action_class: corroborated
file: plugins/cepa/commands/sweep.md
lines: 146
title: "Match against `git branch`" defeated condition 4

**Problem:** `git branch` is porcelain. Verified it emits a
`* (HEAD detached at <sha>)` pseudo-entry and marks a worktree-held branch
with a bare `+` in column 1, indistinguishable from the two-space indent.
Stripping two leading characters yields the correct name with the worktree
signal **lost** — a false listing, the dangerous direction.

**Fix:** `git for-each-ref --format='%(refname:short)' refs/heads/` for
names; `git worktree list --porcelain` for held state, separately.

### 4
status: applied
severity: P2
agent: adversarial-reviewer, silent-failure-hunter
category: correctness
confidence: 90
action_class: corroborated
file: plugins/cepa/commands/sweep.md
lines: 148-155
title: Saturation false-positives, and truncation drops what the report ranks first

**Problem:** `count == limit` reports `partial` on an exactly-full window —
verified, this repo has exactly 48 merged PRs so `--limit 48` returns 48. A
warning that fires on a complete window trains the operator to ignore it.
Separately, `gh` returns newest-first, so truncation drops the **oldest** —
which Step 6 sorts to the top as the safest targets.

**Fix:** request limit+1, report partial only when the count exceeds the
window; a partial window states that oldest-first ordering is within-window
only.

title: Ready-to-run block leaked a fatal and misdiagnosed every non-match

**Problem:** an already-deleted branch printed `fatal: ambiguous argument`
before the SKIP (chain verified safe, but a wall of git fatals reads as
broken commands). The SKIP message hardcoded "tip moved; it has unmerged
work" — fired on every non-match including the already-deleted branch, the
most likely case when re-running a partly-applied list. A lying failure path
that sends the operator hunting for work that does not exist.

**Fix:** `--verify --quiet`; observed-vs-expected reporting; quoted branch
assignment; worktree re-check added; explicit statement that the block
re-verifies the local half only, since `headRefOid` is frozen at report time.

### 6

title: No omission bucket for a condition check that failed to execute

**Problem:** the reason classes covered only branches failing a named
condition. A branch whose `git rev-parse` or worktree read errored had no
bucket — a tooling failure filed as an ordinary omission, or dropped from
the tally entirely.

**Fix:** added `condition unverifiable — <command> failed` as an explicit
class; one branch's failed check omits that branch with the reason and never
aborts the source or shrinks the count silently.
