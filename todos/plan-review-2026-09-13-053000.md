# Plan review — CAP_RC is a declared output that nothing reads

Both always-on personas independently found the same defect, from opposite
directions: the plan's Assumptions section asserted a selftest baseline it had
never run. Coherence caught it as an internal contradiction with the U1 test
table; feasibility caught it by executing the suite. Merged as one finding at
the higher severity.

### 1
status: applied
severity: P1
agent: coherence, feasibility
category: correctness
confidence: 100
action_class: mechanical
file: docs/plans/2026-09-13-cap-rc-unread-output.md
lines: 47, 62-63
title: The plan stated a 30/30 selftest baseline that does not exist

**Problem:** the Assumptions section claimed "Adding one assertion therefore
moves `30/30` to `31/31`", and the U1 test-scenario table promised trailers of
`31/31` (green) and `30/31` (deliberately red). The real baseline, verified by
running `bash scripts/run-mutation-sweep.sh --selftest` on the unmodified tree,
is **38/38**. Every stated number was wrong by eight.

The 30-count appears to have been read off the `29/30` / `30/30` strings at
`scripts/run-mutation-sweep.sh:580,585` — which are *fixture transcripts fed to
`classify_transcript`*, not this suite's own assertion count. The plan's own
Assumptions section says exactly that about those lines, and then uses their
number anyway. That is the contradiction coherence anchored on.

Consequence: an implementer following the verification step literally reads a
trailer that does not match the documented expectation, and has to work out
unaided whether the change or the plan is wrong.

**Fix applied:** the counts are not corrected to 38 — they are removed. The
repo's own CLAUDE.md Critical Rule says *"Do not add new count claims; prefer
wording that doesn't restate totals"*, and a plan that hardcodes 38 is the same
defect one run later. Assumptions now says the trailer's numerator and
denominator each increment by one; the test table states the expected values
relative to the pre-change run.
