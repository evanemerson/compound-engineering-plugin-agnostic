Six review agents plus the learnings researcher. **The three most serious
findings are self-inflicted instances of the exact defect class this harness
exists to catch: a check that reports a clean pass having asserted nothing.**
Two were reproduced empirically before being fixed.

All P1 and P2 findings are applied in `6fff3ca`. Four are deferred as judgment

### 1
status: applied
severity: P1
agent: silent-failure-hunter
category: correctness
confidence: 95
action_class: mechanical
file: .github/workflows/mutation-sweep.yml
lines: 91-95
title: The workflow could never have completed a single run

**Problem:** `run:` steps execute in `$GITHUB_WORKSPACE`, which *is* the
checkout, so `tee sweep.log` created an untracked file in the repo root before
the driver reached its own quiescence gate. That gate then refused to run on a
dirty tree under CI. Reproduced verbatim:
`FATAL: the tree is dirty under CI ... ?? sweep.log`, exit 2, **zero mutants
executed**, deterministically, every week. The observer then compounded it by
reporting `(none named — the run died before classifying)`, which is true but
names the wrong cause.

**Fix:** log to `$RUNNER_TEMP/sweep.log` and read it from there. Explicitly
NOT `--allow-dirty` (it would make the run pass while its own header printed
`LOCAL (dirty at …) — not a gate result`) and NOT a `.gitignore` entry (a rule
at the repo root would also hide a genuinely mutated checker).

### 2
status: applied
severity: P1
agent: adversarial-reviewer, silent-failure-hunter
category: correctness
confidence: 98
action_class: corroborated
file: scripts/run-mutation-sweep.sh
lines: 243-247
title: A control that could not be set up was credited as a control that caught the mutant

**Problem:** `CAUGHT` was decided by `grep -cE '^FAIL  '` alone, but the
harness emits that token for infrastructure failures too — `could not copy
fixture` and `plant step failed or landed as a no-op` — and still prints its
trailer. Reproduced by the reviewer with opposite verdicts on one mutant:

```
RUN A (one env-failed control):  CAUGHT               t-err-half   exit=0
RUN B (harness untouched):       SURVIVED-UNDECLARED  t-err-half   exit=1
```

With 21 undeclared survivors on the books, two environmentally-failing
controls on a hosted runner would have flipped the entire recorded backlog to
`CAUGHT` in one run, turned the sweep green, and left the observer silent.

**Fix:** setup failures now go through a new `error_case()` emitting
`ERROR  <id>` plus a `-- N setup errors --` line; the classifier checks that
**before** the trailer branch and returns `HARNESS-ERROR`. Re-verified: the
same simulation now aborts with exit 2 instead of reporting `CAUGHT`/exit 0.

### 3

category: correctness
confidence: 85
action_class: corroborated
file: .github/workflows/mutation-sweep.yml
lines: 71, 92, 105
title: A timed-out job skips the observer, making the worst outcome the quietest

**Problem:** a job exceeding `timeout-minutes` is **cancelled**, not failed, so
`if: failure()` never fires and the issue step is skipped. On a `schedule:`
trigger that produces no PR check and no notification, "the sweep did not
finish" became indistinguishable from "nothing happened this week" — the exact
off-switch the observer was added to catch. Compounded by `timeout-minutes:
120` sitting *below* the workflow's own stated 3× bound (3 × 42 = 126).

**Fix:** `if: failure() || cancelled()`; job bound raised to 180 with a
step-level 150 on the sweep so the step trips first while the job is still
alive to run the observer.

**Problem:** `c=$(cat -- "$1"; printf X) || return 1` takes `printf`'s status,

file: scripts/run-mutation-sweep.sh
lines: 358, 519-524
title: Quiescence could not see a mid-run edit to an already-dirty file

**Problem:** `git status --porcelain` emits a status code and a path, never
content — so for a file already modified at start, further edits leave the line
byte-identical and the end-of-run comparison sees nothing. **That is exactly
the mid-edit-on-the-checker case D5 was designed for**, stated backwards in the
design comment. The clean→edit→revert shape from the `helm` cross-repo memory
is the same hole.

**Fix:** hash every distinct registered target with `git hash-object` at start
and at exit, and compare that alongside the status.

category: correctness
confidence: 95
action_class: corroborated
file: scripts/run-mutation-sweep.sh
lines: 473-476
title: The apply-write was non-fatal while the identical restore-write was fatal

**Problem:** `>` truncates on open, so a write failing partway (ENOSPC, quota,
EIO) left a truncated checker — and the handler recorded `HARNESS-ERROR` and
`continue`d **without restoring**. Every later mutant reads that file as its
"original" body, producing false `ANCHOR-MISSING` and `BASELINE-DIRTY`
verdicts, both of which tell the operator to re-anchor a registry that is
correct. The restore path nine lines below already stated this reasoning.

**Fix:** fatal, and atomic — write to `$target.mut`, then `mv`. Restore now
also verifies the result is byte-identical rather than trusting printf's exit.
