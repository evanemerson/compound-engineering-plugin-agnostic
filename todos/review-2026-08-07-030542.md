# Plan Review Findings — 2026-08-07 03:05

Panel of six personas over `docs/plans/2026-08-06-runner-runtime-detector.md`.
Origin downgraded to `none` (see Run Metadata), so premise scrutiny was on.

**This review is a blocked-stop, not a revise-and-continue.** Two independent
personas challenged the plan's central premise and the challenge holds up under
direct verification. The plan proposes to *reconstruct* a fact that GitHub
already publishes. Nothing was applied to the plan: applying the mechanical
fixes would have improved a design the panel says is the wrong shape.

**The durable lesson, and it is the same one this repo keeps paying for:** the
plan asserted "nothing fails, warns, or notices" without checking whether the
platform already notices. It does. The real defect was never a missing signal —
it was an **existing authoritative signal with no observer**, which is precisely
the finding this repo already fixed one layer up for the weekly mutation sweep.
The plan reproduced the defect class it was written to close.

## Findings

### 1
- status: deferred

- lines: 7-20
- title: The premise "nothing warns or notices" is false

**Problem:**
Raised independently by product-lens and adversarial, and verified directly
against GitHub's own changelog rather than taken from either agent. The runner
already emits a `::warning::` annotation naming the affected actions by name:

> Node.js 20 actions are deprecated. ... The following actions are running on
> Node.js 20 and may not work as expected: `actions/checkout@v4`,
> `actions/cache@v4`, `actions/setup-python@v5`, `actions/upload-artifact@v4`.

GitHub Changelog, "Deprecation of Node 20 on GitHub Actions runners"
(2025-09-19), with the same 2026-09-16 removal date the plan cites, and the same
mechanism used for the Node 16 → 20 transition in 2023. Runners begin defaulting
to Node 24 on 2026-06-16.

This repo's workflows have been running throughout — `model-pins.yml` on every
PR and push, `mutation-sweep.yml` weekly — while pinned to `actions/checkout`
v4.4.0. So GitHub was almost certainly emitting this exact annotation, naming
this exact action, in this repo's own run logs, for months before a human asked
about it by name.

The plan's "warns" and "notices" clauses are therefore wrong. The signal existed.
Nobody was watching it.

**Fix:**
Do not reconstruct the fact. Observe the one that exists. The runner's
determination is authoritative (it is what actually executes the action), needs
no annotation convention, no policy table, no removal-date list, no self-expiry
bound, and no upstream fetch — and it updates itself for node24 → node28 with no
edit here. The remaining real gap is exactly what the plan's Problem section
gets right: GitHub *warns* but never *fails*, and a warning inside a job log has
no observer. That gap is one job reading its own repo's recent run annotations
and escalating them — the same shape as `sweep-freshness`, in the same file, with
the same `actions: read` scope it already grants.

### 5
- status: deferred
- severity: P1
- agent: adversarial
- category: Adversarial
- confidence: 75
- action_class: judgment
- file: docs/plans/2026-08-06-runner-runtime-detector.md
- lines: 72-80
- title: MISS escalation reddens every unrelated PR for the whole window

**Problem:**
`model-pins.yml`'s `check` job is deliberately not path-filtered and runs on
every `pull_request` and every `push` to main. Once a runtime enters the
escalation window, every PR — including ones touching nothing near workflows —
goes MISS for the entire window. The plan calls this "the point". Against it:
autonomy §9f already reasoned that "failing unrelated PRs is how a signal gets
routed around", and CLAUDE.md treats a red check as blocking even though `main`
is unprotected. A ~6-week red streak trains reviewers to override the check
before the deadline that matters arrives.

**Fix:**
Escalate in two stages rather than one: WARN for the lead time with a durable
side channel (the issue-filing pattern `mutation-sweep.yml` already uses), and
MISS only inside a short hard window near the removal date.

**Problem:**

### 10
- status: deferred
- severity: P2
- agent: security-lens
- category: Security
- confidence: 50
- action_class: judgment
- file: docs/plans/2026-08-06-runner-runtime-detector.md
- lines: 88-92
- title: owner/repo validation regex admits `.` and `..` segments

**Problem:**
`^[A-Za-z0-9._-]+/[A-Za-z0-9._-]+$` accepts `.` and `..` as whole path
components, so `..` passes the guard whose stated job is keeping unexpected
values off the command line, and is then spliced into
`repos/<owner>/<repo>/contents/...`. Not demonstrated exploitable — whether `gh`
or the API edge collapses dot segments is untested.

**Fix:**
Reject any component that is exactly `.` or `..` or contains `..`, ahead of the
existing check. Moot if finding 1 is accepted and no repo-derived value reaches
an argument position.

## Residual risks (recorded, not findings)

- A composite action's nested `uses:` are not followed. The plan states this as a
  limit; the repo pins no composite actions today.
- `model-pins.yml`'s `run:` steps are part of the workflow YAML, so a fork PR
  runs its own version of them, GH_TOKEN and all. The existing `sweep-freshness`
  comment already accepts this ("the bound is GitHub's, not ours"); a new job
  inherits it rather than introducing it.
- `check-action-runtimes.sh` would run from the PR branch, so a PR could edit the
  checker's own policy table to make its stale pin look compliant — the same
  self-modifying-checker exposure `check-model-pins.sh` already has in this
  unprotected-main repo.
