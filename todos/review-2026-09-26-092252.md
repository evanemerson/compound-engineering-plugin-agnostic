# Review — PR #71 (forced PHI-scrub verification + compound-refresh fix)

Reviewed the PR that adds a PHI-scrub step and executable gate to
`/cepa:compound-refresh`'s brain writeback. Five agents dispatched: three
Active-roster, two conditional.

**The review found a P1 in the fix itself.** The gate PR #71 shipped left the
`mv` unchecked, which reintroduced the exact leak the PR existed to close.
Fixed in `22748bb` and re-verified.

---

### 1

- status: applied
- severity: P1
- agent: silent-failure-hunter
- category: correctness
- confidence: 95
- action_class: corroborated
- file: plugins/cepa/commands/compound-refresh.md
- lines: 334-344
- title: Unchecked `mv` fell through to writeback with the unscrubbed original

**Problem:** The scrub gate wrote to a sidecar then ran a bare
`mv "$PAYLOAD.scrubbed" "$PAYLOAD"` with no exit-status check, in a block that
set no shell options. On `mv` failure execution fell straight through to
`writeback "$PAYLOAD"` — and at that point `$PAYLOAD` still holds the
**pre-scrub original**: intact, well-formed, and NON-empty. `_assert_envelope`'s
empty-file check therefore passes it and the unscrubbed content egresses with
every exit code reading 0.

The PR's own defense-in-depth argument was wrong on this path. The empty-file
backstop only ever covered the scrub-truncates-to-zero case; it does not cover
an intact original surviving a failed `mv`. `mv` fails for ordinary reasons:
sidecar removed by a concurrent run, unwritable destination, `EXDEV` across a
container mount, full disk.

Reproduced 2026-09-26 — with the `mv` ungated, `writeback` was handed a payload
still containing `123-45-6789`.

**Fix:** Applied in `22748bb`. Gate the `mv` explicitly and suppress the
writeback on failure; add `set -euo pipefail` to the block (as `compound.md`'s
writeback block already has). The two are not redundant — `-e` is the first
thing a copied fragment loses. Re-verified in isolated shells: `mv` failure
suppresses and the pre-scrub original is not sent; happy path still redacts.

### 2

- status: applied
- severity: P1
- agent: silent-failure-hunter
- category: correctness
- confidence: 85
- action_class: corroborated
- file: plugins/cepa/commands/compound-refresh.md
- lines: 334-344
- title: `$PAYLOAD` was an unassigned bare reference in a multi-doc loop

**Problem:** `$PAYLOAD` appeared only as a bare reference with a comment
calling it "the built envelope" — no assignment, no per-doc uniqueness
requirement. Phase 3 is a multi-document loop. If the executing agent reuses
one path across iterations, a sidecar left by an earlier iteration can be
`mv`'d onto a later doc's payload and posted under the wrong doc's identity.
That substitution is rc=0 end to end and invisible in the transcript — a
provenance corruption, not just a leak risk.

**Fix:** Applied in `22748bb`. Create `$PAYLOAD` fresh per document via
`mktemp`, with the reuse hazard stated explicitly in the block comment.

- confidence: 95

- title: `compound.md`'s PHI scrub is prose only — no executable scrub call exists

**Problem:** Surfaced by the security agent and verified directly: `grep` for
`brain-client.sh` in `compound.md` returns exactly ONE hit — line 170, inside
a narrative instruction. Its executable writeback block resolves `$CEPA_ROOT`,

This is the same defect class PR #71 fixes in the sibling, still live in the
file used as the reference implementation. The plugin-root residual's ruling
applies verbatim: "a guard expressed as prose in a command contract is not
enforcement." `compound.md` is the PRIMARY writeback path — it runs on every
`/cepa:compound` — so after this PR the forced scrub is code-enforced only in
refresh.

**Fix:** Add the same gated block (scrub → gated `mv` → writeback) next to the
`idkey` call that already operates on `$P`. That block already sets
`set -euo pipefail`, so only the explicit gates are needed. Deferred to keep
this PHI-leak fix reviewable — filed as residual item 2b, and it is the
immediate next PR.

### 5

- action_class: mechanical

- title: `scrubbed:`/`suppressed_writebacks:` counts have no counting mechanism

**Problem:** The text instructs the agent to count redactions into `scrubbed:`
and suppressions into `suppressed_writebacks:`. `brain-client.sh scrub` emits
no redaction count, so both fields are whatever the agent writes — skippable,
undercountable, or fabricable with no trace. An operator auditing a compliance
repo's Run Metadata sees `scrubbed: 3` with nothing to check it against.

**Fix:** Applied — the call site now labels both counts self-reported and says
plainly not to cite `scrubbed: N` as evidence that scrubbing occurred. Making
them real (teach `scrub` to emit a count, sum it mechanically) is filed as
residual item 2d.

- title: Prose said scrub "every successor string"; the code scrubbed the whole envelope

**Problem:** The instruction and the code block described different
operations, and the difference is not cosmetic — `sed` cannot tell content
bytes from envelope metadata. Measured 2026-09-26:

- `Celery task 4567890 retried after the 2026-09-26 deploy; see PR #1234567`
  becomes two `[REDACTED-PHI-ID]`s and a `[REDACTED-PHI-DOB]`. Ordinary

  `scrubbed: 3` reports it as successful protection.
- A numeric `BRAIN_WORKSPACE_ID` is itself rewritten to `[REDACTED-PHI-ID]`,
  which 400s the call and then disables the brain for the rest of the run
  under the mid-run degrade rule. Nothing requires that value to be
  non-numeric; the current one survives only because it contains letters.

**Fix:** Applied in `1d56e83`. Prose now says "the built payload FILE", and
names both costs explicitly — whole-file scrubbing cannot forget a string, at
the price of mangling innocent digits.

command's existing "continue to the next doc" rule, with one payload per
