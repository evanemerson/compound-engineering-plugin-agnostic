# Review — PR #32, the 21 control gaps and the decisions that gated them

Second review of this branch, scoped to the five commits after
`todos/review-2026-08-01-123412.md`: `a825734` (exit 3), `2a53dbf` (freshness
detector), `47eee63` (18 controls), `6b28a56` (3 declared survivors),
`8a40e6a` (freshness JSON fix).

**The durable lesson repeats for a third round.** The single P1 is in the
freshness detector — the component built specifically to catch a silent
off-switch — and it was a silent-pass path of its own. A second finding is a
control whose post-plant assertion was vacuously true. Both were reproduced
before being fixed. Building a detector for a class does not exempt the
detector from the class, and this branch has now demonstrated that three
times in its own history.

**A second lesson is new and belongs to this round: the freeze that made the
evidence trustworthy is what made the record wrong.** Freezing
`run-mutation-sweep.sh` and `registry.sh` across the control commit was
correct — it is what makes every `SURVIVED-UNDECLARED -> CAUGHT` flip
attributable to a control. But the prose in the frozen file described a world
the same PR had ended, and nothing reconciled it afterward. Two independent
agents found it; one traced a six-step sequence in which a future editor
prunes a real control, reads the stale `why`, and greens the sweep.

Full sweep after every fix, clean tree at `c4fcd42`, gate result:
**58 CAUGHT / 5 SURVIVED-DECLARED / 0 undeclared / 0 anchor-missing /
0 baseline-dirty / 0 harness errors, exit 0.**

title: An unparseable run timestamp exited 0 with no warning at all

**Problem:** `age=$(( ( $(date -u +%s) - $(date -u -d "$out" +%s) ) / 86400 ))`
inlines the parse into the arithmetic. On a parse failure three things fail in
sequence and none stops anything: `set -e` does not abort on an arithmetic
error inside an assignment, so `age` is left empty; `[ "" -gt 16 ]` errors with
status 2; and an `if` reads that error as false, so control falls to the
`else` — the reassuring branch. The step emitted no `::warning::`, exited 0,
and printed `mutation sweep last ran  days ago` with a blank number. Reproduced
verbatim under GitHub's default `bash -e` shell with a stubbed `gh`.

Reachability is low today (ubuntu-latest, GNU `date`, ISO-8601 from the API)
but this is the sole detector for a failure mode that is otherwise completely
invisible, and it is one runner change from printing that line forever.

**Fix:** parse into `ts` and gate on it, warning and exiting 0 when it cannot
be parsed. All four paths (unparseable / stale / fresh / no successful run)
re-verified under `bash -e`.

### 3
status: applied
severity: P2
agent: adversarial-reviewer
category: security
confidence: 78
action_class: judgment
file: .github/workflows/model-pins.yml
lines: 44-52, 99-106
title: GH_TOKEN shared a job with PR-authored scripts

**Problem:** `model-pins.yml` runs on `pull_request`, and its steps 2-3 are
`bash scripts/check-model-pins.sh` and `bash scripts/check-model-pins-controls.sh`
— both read from the PR head, so both are attacker-authored on a fork PR.
Before this PR the job held no credential. The freshness step introduced
`GH_TOKEN`. `$GITHUB_PATH` written by one step is prepended to `PATH` for every
later step in the SAME job, so a fork PR could append a `gh` shim and receive
the token in its environment. Bounded today — GitHub forces fork
`pull_request` tokens read-only regardless of the `permissions:` block — but
that bound is GitHub's, not ours, and the file's own header argued "no
injection surface" from `${{ }}` interpolation, which was never the surface.

**Fix:** moved to its own `sweep-freshness` job with job-scoped
`actions: read` and no checkout. A separate job shares no PATH, no filesystem
and no working tree. The header comment now states what actually bounds the
risk.

### 12
status: deferred
severity: P2
agent: reliability-reviewer
category: reliability
confidence: 85
action_class: judgment
file: scripts/run-mutation-sweep.sh
lines: 623
title: The nested per-mutant timeout cannot reach a hung checker

**Problem:** GNU `timeout` without `--foreground` puts its child in a new
process group. The sweep's `timeout -k 30 900 bash controls.sh` therefore
signals only that process group — while the controls suite's own nested
`timeout 120 bash "$CHECKER"` has already moved itself into a third. Verified
empirically: after an outer timeout SIGKILLs its child, the grandchild and its
`timeout` survive as orphans, and the child's `trap ... TERM` never fires
because bash defers traps until the foreground command completes. Because the
orphan still holds the pipe `out=$(...)` reads, worst case for one mutant is
~1050s rather than the 930s the code's accounting implies, and that
invocation's fixture tree (with mode-000 files) is orphaned meanwhile.

Does NOT produce a false CAUGHT — the truncated transcript has no trailer, so
it classifies as `HARNESS-ERROR` and the run exits 2. And it is **latent**: no
currently registered mutant targets the construct case 32 guards, so nothing
in today's 63 triggers it.

**Fix:** needs a design call — `-k` on the inner timeout, `--foreground` or
process-group-aware killing, or accepting the current soft bound with the
limit recorded. Deferred as judgment; carried to the residual shard.
