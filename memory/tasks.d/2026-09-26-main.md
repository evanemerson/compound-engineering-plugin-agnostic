1. **OB1 Agent Memory API: recall cannot identify a doc's prior memories —
   `mark_stale` is therefore only ever partial.** Capability gap in the
   SERVICE, not in cepa. PR #70 (v1.26.5, `a815590`) fixed the *contract* to
   stop instructing an impossible lookup; it did not and could not fix the
   underlying limitation.

   **The gap.** `mark_stale` is `:id`-addressed. Recall never projects
   `source_refs` into its response and returns `source.uri: null` on every
   hit, so there is no query that answers "which memories came from this
   doc". `scope.project_id` is the only provenance returned, and it is
   repo-grained — every memory the repo ever wrote, not this doc's.

   Measured twice against the deployed Edge Function:
   - 2026-08-22 — 10 hits across two repos, no `source_refs` on any,
     `source.uri` null on all.
   - 2026-09-26 — 5 hits, same result, on rows written earlier that same day.

   **Consequence, now documented as the honest ceiling.** A doc edited by a
   run that does not hold the original `memory_id`s cannot have its pre-edit
   rows retired. Those rows keep being served by recall alongside the new
   ones. v1.26.5 makes this visible rather than silent — the producer writes
   the new strings anyway and records
   `mark_stale: skipped — no path-identifiable prior rows` in the `brain` Run
   Metadata block — but visible staleness is still staleness.

   **The real remedy is server-side, and is one of:**
   - project `source_refs` (or at minimum the `uri`) into the recall
     response, so a caller can filter by doc path; or
   - expose a by-source query / `DELETE`-by-source on the writeback API; or
   - return prior row ids in the writeback response when an
     `idempotency_key` base matches existing rows, so a producer learns the
     ids it needs at the moment it needs them.

   The third is the cheapest and fits the existing flow: the producer already
   posts a stable content-hash idkey, so the service already knows which
   prior rows share that base.

   **Interim mitigation available without a server change:** record the
   returned `memory_id`s in the solution doc's own Run Metadata (or the run's
   residual shard) at write time, so a later editing run has ids to retire.
   Not implemented — it would need a writeback-time contract change in
   `/cepa:compound`, and is only worth doing if the server fix is far off.

   **Do NOT "work around" it with a `scope.project_id` recall.** That returns
   every memory the repo ever wrote; stale-marking its hits retires unrelated
   knowledge. Forbidden explicitly at all three contract sites in v1.26.5.

   Found by: an artist360 session running `/cepa:compound` to test the
   writeback path, which stopped before writing and reported the blocker
   rather than producing a green run. Contract fix: PR #70. Related:
