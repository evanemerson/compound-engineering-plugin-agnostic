### What went wrong here, and it is worth keeping

This session read the shard's "2 of 4" status line, re-verified that
`actions/checkout@v7` and `actions/setup-node@v7` still resolve as node24 refs,
and wrote two paste-ready hand-off prompts for work that had already shipped
three days earlier. The operator caught it.

Two distinct failures, both recorded in the sweep shard itself:

1. **The wrong invariant.** Verifying the *prescription* (does the tag resolve?
   what runtime does it name?) is what that shard demands, and it passed. It
   does not answer whether the *target still needs the change*. Fourth instance
   of `checking-the-wrong-invariant-reads-exactly-like-checking-the-right-one`
   in this repo — and the second one to occur *inside* work on that very lesson.
2. **A PR list is not a completion check.** `dpc-pro`'s fix was a direct commit,
   so `gh pr list` showed nothing and the first pass concluded the pin was still
   owed. The workflow file is the authority on what a workflow pins.

**Generalizable, and the reason this is filed rather than dropped:** a residual
shard is a *cache of another repo's state*, and it goes stale silently. Nothing
in the sink expires, marks itself uncertain, or distinguishes "verified today"
from "verified when written." A tracked work list that reads as current is more
dangerous than a missing one, because it is actionable. Before acting on any
cross-repo shard item, re-read the target's current state — for CI pins that is
one `gh api .../contents/.github/workflows/<f>` call per repo, no boundary-rule
tension, and it is the only check that answers "is this still owed."
