1. **The installed plugin copy silently lags `main` after a merge.** P2.
   **FIXED in v1.26.11 (`1699104`)** — `scripts/check-plugin-freshness.sh`,
   wired into `/cepa:setup` check 4 and CLAUDE.md § "A merged fix is not a

   **Correction to this item's own diagnosis: there are TWO hops, not one.**
   This item said the refresh is
   `git -C ~/.claude/plugins/marketplaces/cepa pull --ff-only`. That is hop 1
   only. Claude Code does not load the clone — it loads a versioned cache at
   `~/.claude/plugins/cache/cepa/cepa/<version>/`, populated by
   `claude plugin update cepa@cepa`. Measured 2026-09-28 while building the
   check: the clone was ALREADY at v1.26.10 (someone had pulled it) while the
   loaded cache was still the v1.26.5 tree, whose `compound.md` carries the
   PHI scrub as prose only — the exact defect 2b. So the fix this item
   prescribed would have reported that state clean, and the PHI fixes would
   still not have been live. Retained as the record of what was wrong.

   The check compares commit SHAs, not version strings: `installed_plugins.json`
   records the `gitCommitSha` the cache was built from, and that is the
   authority on what a `/cepa:*` invocation executes. A version compare fails
   in both directions — repo-root docs do not bump the manifests, so versions
   match while plugin commits sit unshipped.

   Verified: rc=1 on the real stale state and on a rewound clone; rc=0 when the
   cache is current, and when `main`'s tip is a docs-only commit (the
   false-positive this repo's version-scope convention creates). Absent
   `python3`, absent/garbage JSON, and a SHA from another remote all report
   `UNKNOWN` at rc=0 — a checker that fails closed on a missing optional tool
   trains people to skip it.

   Not gateable in CI: it measures one developer machine's local install
   state, which no runner has and no commit can fix.

   On 2026-09-27, `~/.claude/plugins/marketplaces/cepa` sat at `a815590`
   (v1.26.5) while `main` was at v1.26.10 — three releases behind. So the
   PHI-scrub fixes from PRs #71 and #72 were **not live** in the plugin
   Claude Code actually loads, for the whole session that wrote them. It was
   caught only because the session compared the two HEADs by hand.

   Nothing warns about this. `gh pr merge` moves GitHub, the local `main`
   pull moves this checkout, and the marketplace clone moves only when
   someone pulls it. It is a clean clone of this same repo on `main`, so the
   refresh is `git -C ~/.claude/plugins/marketplaces/cepa pull --ff-only`.

   **Why it matters beyond convenience:** a session can merge a security fix,
   verify it on `main`, report it shipped, and still be running the old code
   on the next invocation. Every claim of "verified against the installed
   copy" is only as good as that copy being current.

   Fix: a check that compares the marketplace clone's HEAD against the repo's
   last plugin-touching commit and says so loudly when they differ. The
   handoff's verification block already contains the exact comparison; it
   just is not enforced anywhere.
