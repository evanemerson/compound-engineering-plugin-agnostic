### Open

- [ ] P2 — **`cepa:file-todos` has no status for "resolved because the reviewed
  artifact was superseded".** The Status Lifecycle offers `deferred → completed
  (fixed later in a dedicated pass)` and `→ skipped` (human triage: *removed from
  file*; or the `/cepa:resolve-pr` verdict edge, which retains). None of those is
  what happened to findings 2, 3, 4, 7, 9, and 10 here: nobody fixed them, and
  they were not rejected — the plan they critiqued was discarded, so the defect
  ceased to exist. `completed` was used because it is the only terminal state
  that retains the finding and reads as closed, with the reason carried in
  `resolved:` prose. That is a prose workaround for a missing enum value, which
  is the shape `a-closure-claim-in-prose-is-not-the-field-a-consumer-parses`
  warns about — the machine-parsed field cannot distinguish "fixed" from "the
  subject evaporated", so any future metric over `completed` overstates work
  done. Options: add `superseded` to the enum, or state explicitly in the spec
  that `completed` covers it and require the `resolved:` prose to say which.
  **Not decided here** — it is a change to the canonical findings spec, which
  wants its own PR.

- [ ] P3 — **plan-review findings outlive their plan with no link back.** These
  findings named `file: docs/plans/2026-08-06-runner-runtime-detector.md`, and
  `docs/` is gitignored, so a reader on a fresh clone cannot open the artifact
  the findings describe or discover it was superseded. Nothing in the findings
  file recorded the supersession until this pass. A `superseded_by:` frontmatter
  field on plan-scoped findings files would make it discoverable; the cheaper
  half is a convention that the PR replacing a plan updates the prior review
  file's `triage:` line. Related to the P2 above but separable.
